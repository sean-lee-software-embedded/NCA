Domain 1: AI 計算架構與訓練推理對比

Compute Architecture, Precision Formats & Training vs. Inference Lifecycle

1.1 CPU vs. GPU 核心微架構哲學 (Hardware Architecture)

CPU (Central Processing Unit)： 專為低延遲（Low Latency）與順序指令執行而設計。具備少數高時脈核心、龐大的快取記憶體（L1/L2/L3 Cache）以及複雜的分支預測（Branch Prediction）與亂序執行（Out-of-Order Execution）控制邏輯。

GPU (Graphics Processing Unit)： 專為高吞吐量（High Throughput）的大規模平行計算（SIMD/SIMT - Single Instruction, Multiple Threads）而設計。將絕大部分晶片面積分配給 ALU（算術邏輯單元）與專用 Tensor Cores。

硬體特性 CPU (例如 Intel Xeon / AMD EPYC) GPU (例如 NVIDIA H100 / A100 / L40S)
核心數量 十至上百個大型通用核心 數千個 Stream Processors + 數百個 Tensor Cores
記憶體頻寬 DDR5 (~200 - 400 GB/s) HBM3 / GDDR6 (高達 2.0 - 3.35 TB/s)
優化目標 極致優化單執行緒延遲 (Single-thread Latency) 極致優化矩陣平行吞吐量 (Parallel Throughput)
AI 工作負載 數據預處理、ETL、邏輯控制、輕量 ML 推理 深度學習模型訓練、大規模 LLM 推理加速

1.2 Training vs. Inference 運算生命週期

訓練階段 (Training Phase)

  • 目標： 從數據中學習權重（Weights & Biases），優化 Loss Function。
  • 計算特性： 包含前向傳播 (Forward Pass) 與反向傳播 (Backward Pass)。需要保存中間激活值 (Activations) 以計算梯度 (Gradients)。
  • 算力需求： 極高 FLOPS 與顯存需求，通常採用多卡多機 Distributed Training (Data Parallelism, Tensor Parallelism)。

推理階段 (Inference Phase)

  • 目標： 給定輸入，利用已鎖定的權重產出預測或生成內容。
  • 計算特性： 僅執行前向傳播 (Forward Pass)，無須反向傳播，不保存梯度。
  • 性能指標： 嚴格的要求首字延遲 (TTFT)、每秒 Token 數 (TBT) 以及併發吞吐量 (QPS)。

1.3 數值精度格式 (Precision Formats: FP32, FP16, BF16, INT8, FP8)

數值精度直接影響 GPU 顯存佔用、記憶體頻寬需求以及 Tensor Core 計算速度：

  • FP32 (Single Precision)： 1 Sign + 8 Exponent + 23 Mantissa (32-bit)。傳統訓練基準，精度高但消耗資源。
  • FP16 (Half Precision)： 1 Sign + 5 Exponent + 10 Mantissa (16-bit)。顯存節省一半，但指數範圍小，易發生下溢 (Underflow)。
  • BF16 (Bfloat16)： 1 Sign + 8 Exponent + 7 Mantissa (16-bit)。保留與 FP32 相同的動態範圍，深度學習訓練的黃金標準。
  • INT8 (8-bit Integer)： 8-bit 整數。推理專用，顯存需求降至 1/4，搭配 Tensor Core 可達成數倍吞吐量。
  • FP8 (Float 8)： Hopper 架構引入。分為 E4M3 (適用於 Activation/Weight) 與 E5M2 (適用於 Gradient/Gradients 傳播)。

Domain 2: NVIDIA TensorRT 推理優化實作

TensorRT Engine Building, Layer Fusion, Quantization & trtexec CLI

2.1 TensorRT 架構與核心優化管道 (Optimization Pipeline)

NVIDIA TensorRT 是高效能深度學習推理 SDK，包含優化編譯器 (Optimizer) 與運行時環境 (Runtime)。模型輸入 (如 ONNX) 經過 TensorRT 優化後會生成平台專屬的 Serialized Engine (.engine / .plan)。

TensorRT 五大關鍵優化技術：

  1. Layer & Tensor Fusion (層與張量融合)： 將連續的運算層 (例如 Conv + Bias + ReLU) 融合為單一 CUDA Kernel，大幅降低 GPU Global Memory 讀寫開銷。
  2. Weight & Activation Quantization (權重與激活值量化)： 將 FP32/FP16 模型轉為 INT8/FP8，透過動態或靜態 Calibration 維持 >99% 準確率。
  3. Kernel Auto-Tuning (Kernel 自動調優)： 根據目標 GPU 顯卡 (如 H100, A100, L40) 的硬體微架構，挑選最優化的 CUDA Kernel 實作。
  4. Dynamic Shapes Support (動態形狀支援)： 允許 Runtime 時動態改變 Batch Size 及輸入序列長度 (Sequence Length)。
  5. Multi-Stream Execution (多流執行)： 利用 CUDA Streams 實現推理請求的併發重疊執行。

2.2 trtexec 命令列工具實作與參數解析

trtexec 是 TensorRT 官方提供的快速模型轉換與 Benchmark 工具：

# 範例 1: 將 ONNX 模型轉換為 FP16 + INT8 TensorRT Engine 並設定動態 Batch Size
trtexec --onnx=resnet50.onnx         --saveEngine=resnet50_int8.engine         --fp16         --int8         --calib=calib.cache         --minShapes=input:1x3x224x224         --optShapes=input:16x3x224x224         --maxShapes=input:64x3x224x224         --verbose

# 範例 2: 針對 Engine 執行基準效能測試 (Latency & Throughput)
trtexec --loadEngine=resnet50_int8.engine         --batch=16         --duration=10         --avgRuns=100

2.3 TensorRT Python API 建構流程

import tensorrt as trt

# 1. 建立 Logger, Builder 與 Network Definition
TRT_LOGGER = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(TRT_LOGGER)
network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
parser = trt.OnnxParser(network, TRT_LOGGER)

# 2. 解析 ONNX 模型檔案
with open("model.onnx", "rb") as f:
    if not parser.parse(f.read()):
        for error in range(parser.num_errors):
            print(parser.get_error(error))

# 3. 設定 Builder Configuration (啟用 FP16 與 Dynamic Profile)
config = builder.create_builder_config()
config.set_flag(trt.BuilderFlag.FP16)
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30) # 1GB Workspace

profile = builder.create_optimization_profile()
profile.set_shape("input", (1, 3, 224, 224), (8, 3, 224, 224), (32, 3, 224, 224))
config.add_optimization_profile(profile)

# 4. 編譯並序列化 Engine
serialized_engine = builder.build_serialized_network(network, config)
with open("model_fp16.engine", "wb") as f:
    f.write(serialized_engine)
print("TensorRT Engine 成功建立！")

Domain 3: AI 儲存架構與 GPUDirect Storage

Storage Bottlenecks, GPUDirect Storage (GDS), NVMe-oF & Storage Scaling

3.1 AI 訓練與推理的 I/O 儲存瓶頸 (I/O Bottlenecks)

在高階 GPU (如 H100) 算力大幅提升的背景下，傳統儲存系統常成為整個 AI 架構的瓶頸，導致 GPU 算力飢餓 (GPU Starvation)。

儲存需求維度 AI 訓練階段 (AI Training Storage) AI 推理階段 (AI Inference Storage)
存取模式 高併發、大規模順序與隨機混合讀取 (Dataset Reads) 主要為模型載入 (Model Loading) 與 Checkpoint 讀寫
核心效能指標 極高持續吞吐量 (Throughput, GB/s) 與 IOPS 超低讀取延遲 (Latency, ms) 與高高併發
架構建議 並行檔案系統 (Lustre, WekaIO, BeeGFS) + Scale-out NVMe 分佈式物件儲存 (MinIO) / 本地 Fast NVMe SSD Cache

3.2 GPUDirect Storage (GDS) 技術深度解析

傳統 I/O 資料傳輸路徑需要將 NVMe SSD 中的數據先複製到 CPU Host System Memory (RAM)，再經由 PCIe Bus 複製到 GPU VRAM。這會帶來額外的 CPU Context Switch 負擔與延遲。

【 傳統數據傳輸路徑 】
NVMe SSD ──► PCIe ──► Host CPU RAM (bounce buffer) ──► PCIe ──► GPU VRAM
(高 CPU 佔用率、增加記憶體複製延遲、受限於 CPU PCIe 通道)

【 GPUDirect Storage (GDS) 路徑 】
NVMe SSD ──────────────────── (Direct DMA Path) ───────────────────► GPU VRAM
(繞過 CPU RAM，直接使用 PCIe Direct DMA；極低延遲、釋放 CPU 算力)

Domain 4: K8s 雲原生與 NVIDIA GPU Operator

Kubernetes GPU Scheduling, NVIDIA GPU Operator, CRDs & MIG Partitioning

4.1 NVIDIA GPU Operator 運作機制

NVIDIA GPU Operator 利用 Kubernetes 的 Operator Pattern 與 Custom Resource Definitions (CRDs)，自動化管理在 K8s 集群中運行 GPU 所需的所有組件。

GPU Operator 自動部署的核心 DaemonSets：

  • NVIDIA Driver Container： 動態編譯並載入宿主機的 NVIDIA GPU 驅動。
  • NVIDIA Container Toolkit： 設定容器運行時 (containerd / cri-o)，實現 GPU 設備掛載。
  • NVIDIA Kubernetes Device Plugin： 向 K8s API Server 註冊 nvidia.com/gpu 資源。
  • NVIDIA DCGM Exporter： 收集 GPU 溫度、顯存、功耗等 Metrics 並導出給 Prometheus。
  • Node Feature Discovery (NFD)： 自動打標籤 (Label) 識別 GPU 型號與功能。

4.2 Multi-Instance GPU (MIG) 多實例切分技術

MIG 技術允許將單張實體 GPU (如 A100 / H100) 在硬體層級切分為最多 7 個獨立的 GPU Instances (GI)，各實例擁有獨立的 Tensor Cores、Memory Decoders 與顯存，提供真正的硬體級隔離 (Hardware Isolation)。

4.3 Kubernetes GPU Pod 部署 YAML 範例

apiVersion: v1

      claimName: model-pvc-claim

Domain 5: 企業級 LLM、RAG 與 TensorRT-LLM

LLM Inference Engine, PagedAttention, In-Flight Batching & TensorRT-LLM

5.1 LLM 落地部署三大路徑對比

  • Foundation Models (從頭預訓練)： 成本極高，需上千張 GPU 訓練數月，適合頂尖 AI 研究機構。
  • Fine-Tuning (模型微調 - LoRA / QLoRA)： 凍結基底模型，僅調整低秩矩陣。適合讓模型學習特定格式或領域語氣。
  • RAG (Retrieval-Augmented Generation 檢索增強生成)： 結合外部向量資料庫 (Vector DB)，將私有知識庫作為 Context 輸入。零模型重訓成本、徹底解決模型幻覺 (Hallucination) 與時效性問題。

5.2 TensorRT-LLM 與高效能推理關鍵技術

TensorRT-LLM 是 NVIDIA 針對大語言模型 (LLM) 推理加速的專用庫：

  • PagedAttention： 解決傳統 KV Cache 記憶體碎片化問題。將 KV Cache 切分為固定大小的 Block 頁面，實現動態記憶體分配，將 Batch Size 提升數倍。
  • In-Flight Batching (Continuous Batching)： 傳統 Batching 必須等待 Batch 內最長句子完成才釋放；In-Flight Batching 允許在 Token 生成層級（Iteration-level）動態加入新請求或移出已完成請求。
  • FP8 / INT4 AWQ 量化： 支援 FP8 (E4M3) 與 Weight-Only INT4 量化，大幅降低 LLM 顯存需求並翻倍生成速度。

6. 50 題全真模擬試題與深度解析 (Exam Questions 1-50)

Comprehensive Certification Practice Questions with Detailed Explanations

1. Q1 [Domain 1] 在微架構層面，CPU 與 GPU 最主要的設計哲學差異是什麼？
  • A. CPU 著重於高吞吐量的平行計算，GPU 著重於單執行緒低延遲
  • B. CPU 晶片將大部分面積配置給 ALU，GPU 配有大量 Cache 與分支預測器
  • C. CPU 著重於低延遲與複雜順序邏輯處理，GPU 著重於大規模 SIMT 平行計算吞吐量
  • D. CPU 採用 HBM3 高頻寬記憶體，GPU 採用標準 DDR5 記憶體
查看正確答案與詳細解析
正確答案：C
【深度解析】：CPU 專為低延遲、複雜控制流（分支預測、大快取）設計；GPU 專為高吞吐量 SIMT (Single Instruction Multiple Threads) 平行陣列運算設計。
2. Q2 [Domain 1] 在深度學習模型訓練 (Training) 中，為何需要保存前向傳播的中間激活值 (Activations)？
  • A. 用於在推理時加速 Layer Fusion
  • B. 用於在反向傳播 (Backward Pass) 時計算權重梯度 (Gradients)
  • C. 用於將 FP32 自動量化為 INT8
  • D. 用於備份至 NVMe SSD 防止訓練中斷
查看正確答案與詳細解析
正確答案：B
【深度解析】：訓練階段的反向傳播需要根據鏈式法則 (Chain Rule) 計算梯度，此過程必須使用前向傳播保存的中間激活值。
3. Q3 [Domain 1] 關於 BF16 (Bfloat16) 與 FP16 精度格式的對比，下列何者正確？
  • A. BF16 的 Mantissa 位元數多於 FP16，因此精度更高的
  • B. BF16 保留了與 FP32 相同的 8-bit Exponent，防範梯度下溢能力優於 FP16
  • C. FP16 擁有更高的動態範圍，適用於大模型預訓練
  • D. BF16 佔用的顯存大小是 FP16 的兩倍
查看正確答案與詳細解析
正確答案：B
【深度解析】：BF16 採用 1 Sign + 8 Exponent + 7 Mantissa，指數位與 FP32 一致（8-bit），因此具備與 FP32 相同的動態範圍，非常適合深度學習訓練。
4. Q4 [Domain 1] NVIDIA Hopper 架構引入的 FP8 精度中，E4M3 與 E5M2 的主要適用場景為何？
  • A. E4M3 適用於梯度傳播，E5M2 適用於模型備份
  • B. E4M3 (精度較高) 適用於 Forward Pass 的 Activations/Weights；E5M2 (範圍較廣) 適用於 Backward Pass 梯度
  • C. E4M3 專用於 CPU 運算，E5M2 專用於 GPU 運算
  • D. 兩者結構完全相同，僅名稱不同
查看正確答案與詳細解析
正確答案：B
【深度解析】：E4M3 擁有 4-bit Mantissa (精度高)，適合權重與激活；E5M2 擁有 5-bit Exponent (動態範圍大)，適合梯度。
5. Q5 [Domain 1] 下列哪一項不是模型推理 (Inference) 的典型效能指標？
  • A. 首字生成時間 (Time-to-First-Token, TTFT)
  • B. 每秒 Token 吞吐量 (Tokens-per-second, TPS)
  • C. 反向傳播每秒迭代步數 (Steps Per Second)
  • D. 併發請求服務品質 (QPS / Latency P99)
查看正確答案與詳細解析
正確答案：C
【深度解析】：反向傳播步驟（Steps Per Second）屬於模型訓練 (Training) 的指標，推理階段不執行反向傳播。
6. Q6 [Domain 1] 深度學習矩陣乘法運算 (GEMM) 在 GPU 上最主要由下列哪一個硬體單元加速？
  • A. CUDA Control Core
  • B. Tensor Core
  • C. L2 Cache Controller
  • D. PCIe PHY Bridge
查看正確答案與詳細解析
正確答案：B
【深度解析】：NVIDIA Tensor Cores 是專為矩陣乘加運算 (D = A * B + C) 設計的硬體加速單元。
7. Q7 [Domain 1] 對於 Transformer 模型，在推理階段顯存佔用 (VRAM) 的主要來源不包含下列何者？
  • A. 模型權重 (Model Weights)
  • B. KV Cache
  • C. 反向傳播梯度矩陣 (Gradients)
  • D. 輸入與輸出的 Activation Tensors
查看正確答案與詳細解析
正確答案：C
【深度解析】：推理階段不會計算或儲存梯度 (Gradients)。
8. Q8 [Domain 1] 為何在 GPU 上執行 INT8 推理時通常需要進行 Calibration (校正)？
  • A. 為了將模型檔案大小壓縮 100 倍
  • B. 為了收集 Activation 的數值分佈，計算最佳 Scaling Factor 以降低量化誤差
  • C. 為了修正 CUDA Driver 的相容性問題
  • D. 為了將 INT8 轉回 FP32 進行計算
查看正確答案與詳細解析
正確答案：B
【深度解析】：Calibration 透過輸入少量代表性數據，觀察數據動態範圍，計算動態門檻 (Entropy Calibration) 以將 FP32 對應至 INT8。
9. Q9 [Domain 1] 當 GPU 顯存頻寬成為瓶頸 (Memory-Bandwidth Bound) 時，下列哪種優化手段最有效？
  • A. 增加 CPU 核心數
  • B. 採用模型量化 (如 FP16 降至 INT8) 或 Kernel Fusion
  • C. 換用更高的 PCIe 通道數
  • D. 增加 SSD 容量
查看正確答案與詳細解析
正確答案：B
【深度解析】：量化減少資料傳輸體積，Kernel Fusion 減少 Global Memory 讀寫次數，能直接緩解顯存頻寬瓶頸。
10. Q10 [Domain 1] 在分散式訓練中，Data Parallelism (資料平行) 的核心運作機制為何？
  • A. 將模型層切分部署於不同 GPU，資料依序通過
