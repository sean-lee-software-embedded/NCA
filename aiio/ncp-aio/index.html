4. 怎麼租：NVIDIA Brev

Brev 會從多個 cloud provider 提供 GPU VM。這一階段的重點是少處理 IAM、driver repo、security group 等雜務，快速進入 NVIDIA GPU/Linux 實作。

4.1 macOS 安裝 CLI

brew install brevdev/homebrew-brev/brev
brev --version
brev login

登入會打開瀏覽器。CLI credential 與 SSH keys 會放在 ~/.brev/。

4.2 選 GPU：學習優先，不追最高階

第一週末優先選「價格合理、至少 16–24GB VRAM、一般 CUDA/Docker/DCGM 可用」的 GPU。A10G / L4 / L40S 類型通常已足夠；不要只因為 H100 比較酷就多花錢。

價格不是固定：建立 instance 前，以 Brev Console / CLI 當下顯示為準。不要把教材中的任何 US$/hr 範例當成保證價格。

4.3 建立與登入

# 先在 Brev Console 或 CLI 找當下可用 GPU type
# 官方 quickstart 的 create 語法示例：
brev create ncp-aio-lab --gpu "<AVAILABLE_GPU_TYPE>"

# 進入 Linux shell
brev shell ncp-aio-lab

# 第一個驗證
nvidia-smi

4.4 用完一定 stop

exit
brev stop ncp-aio-lab

# 下次繼續
brev start ncp-aio-lab
brev shell ncp-aio-lab
Cloud GPU 最容易浪費錢的錯誤：忘記 stop。Brev stopped instance 不再收 compute fee，但仍可能有少量 storage 成本；重新啟動也受當下 GPU capacity 影響。重要筆記與 script 建議同步到 Git。

5. Hands-on Labs

Lab 1 — GPU Inventory：先不要跑 AI

目標

先用 System Engineer 的方式把機器 inventory 完整看一遍，再把 GPU 當成一個受管理的 subsystem。

hostname
uname -a
lscpu
free -h
lsblk

nvidia-smi
nvidia-smi -L
nvidia-smi -q
nvidia-smi topo -m

你至少要看懂

  • GPU model / UUID / PCI Bus ID
  • Driver version
  • nvidia-smi 顯示的 CUDA compatibility version 與本機 nvcc toolkit version不是同一件事
  • FB memory used/total
  • GPU utilization
  • Temperature / Power
  • ECC / health related fields（依 GPU 支援）
  • Processes
nvidia-smi --query-gpu=name,uuid,pci.bus_id,temperature.gpu,power.draw,utilization.gpu,memory.used,memory.total --format=csv

watch -n 1 nvidia-smi

# Toolkit compiler version（若 image 有 nvcc）
nvcc --version
驗收：不看文件回答「現在這台機器有幾張 GPU？是哪一型？driver 是什麼？GPU memory 用多少？哪個 process 正在用？temperature/power/utilization 怎麼看？」

Lab 2 — 製造 GPU Load，再看 telemetry

python3 - <<'PY'
import torch
print("PyTorch:", torch.__version__)
print("CUDA available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("GPU:", torch.cuda.get_device_name(0))
    print("GPU count:", torch.cuda.device_count())
PY

若環境沒有 PyTorch，再依 image / Python 環境安裝。不要因為 package conflict 在第一天浪費太多時間；必要時直接使用 NGC PyTorch container 做下一步。

cat > ~/workspace/gpu_load.py <<'PY'
import torch, time
assert torch.cuda.is_available()
print("GPU:", torch.cuda.get_device_name(0))
a = torch.randn(4096, 4096, device="cuda")
b = torch.randn(4096, 4096, device="cuda")
end = time.time() + 60
count = 0
while time.time() < end:
    c = torch.matmul(a, b)
    torch.cuda.synchronize()
    count += 1
print("Iterations:", count)
PY

# Terminal A
python3 ~/workspace/gpu_load.py

# Terminal B
nvidia-smi dmon
# 或
watch -n 1 nvidia-smi
觀察：GPU util ↑、FB memory ↑、power ↑、temperature 變化、process 出現。把「指標」和「workload 行為」連起來。

docker --version

Lab 4 — NVIDIA NGC Container Registry

Professional blueprint 直接包含 deploy containers from NGC 與 troubleshoot NGC deployment。

Login

docker login nvcr.io
# Username 通常使用：$oauthtoken
# Password：你的 NGC API key

Pull / Run

# Tag 會更新，請到 NGC Catalog 選目前存在的 tag
export NGC_PYTORCH_IMAGE='nvcr.io/nvidia/pytorch:<CURRENT_TAG>'

docker pull "$NGC_PYTORCH_IMAGE"

Lab 5 — DCGM：從 nvidia-smi 進入 Data Center GPU Operations

DCGM 提供 data-center accelerator 的 observing、management、validation、diagnostics 與 integration。DCGM Exporter 則把 DCGM fields 暴露成 Prometheus metrics。

最省時間：DCGM Exporter container

export DCGM_EXPORTER_TAG=latest

docker run -d --rm \
  --name dcgm-exporter \
  --gpus all \
  --cap-add SYS_ADMIN \
  -p 9400:9400 \
  nvcr.io/nvidia/k8s/dcgm-exporter:${DCGM_EXPORTER_TAG}

docker ps
curl --fail http://localhost:9400/metrics | head

curl -s http://localhost:9400/metrics | \
  grep -E 'DCGM_FI_DEV_GPU_UTIL|DCGM_FI_DEV_FB_USED|DCGM_FI_DEV_POWER_USAGE' | head -30

再跑一次 Lab 2 的 workload，看 metrics 如何變化。

DCGM Diagnostics（環境有 dcgmi 時）

dcgmi discovery --list
# 查看目前版本支援的 suite / syntax
dcgmi diag --help
# 再依文件選擇適合的 diagnostic suite
dcgmi diag --run 1
Diagnostics 會消耗資源：正式環境執行 active diagnostic 前必須知道影響。Cloud VM 若缺 dcgmi，第一週末先把 telemetry 跑通，不要為 repo/package issue 卡兩小時。

Lab 6 — Slurm：GPU 是怎麼被 scheduler 分配的

slurmctld (controller / scheduler) │ ▼ slurmd │ ▼ Compute Node ── GRES: gpu │ ▼ CUDA_VISIBLE_DEVICES / GPU allocation
先說限制：在單一 Brev VM 自建 single-node Slurm 是「練 CLI / state / GRES / troubleshooting」，不是 production multi-node cluster 的替代品。Ubuntu image 與 Slurm package 版本不同，service/config 細節可能需要依實機調整。

基本安裝與偵測

sudo apt update
sudo apt install -y munge slurm-wlm
sudo systemctl enable --now munge
systemctl status munge --no-pager

# 讓 slurmd 告訴你本機正確硬體參數
slurmd -C

建立 slurm.conf 時，不要亂抄 CPU / memory 數字；使用 slurmd -C 的輸出，再加入你的 controller、partition、GRES 設定。

GPU GRES 核心概念

# 概念示意，實際 NodeName/CPU/Memory 以你的 VM 為準
GresTypes=gpu
NodeName=<HOST> ... Gres=gpu:1
PartitionName=gpu Nodes=<HOST> Default=YES State=UP

# gres.conf 可使用 NVML 自動偵測（依 Slurm build / plugin）
AutoDetect=nvml
Name=gpu File=/dev/nvidia0

一定要熟的 CLI

sinfo
sinfo -R
squeue
scontrol show node
scontrol show job <JOB_ID>

srun --gres=gpu:1 nvidia-smi -L
sbatch --gres=gpu:1 --wrap='nvidia-smi'

故意 Drain，再修回來

HOST=$(hostname -s)
sudo scontrol update NodeName=$HOST State=DRAIN Reason="NCP-AIO practice"

sinfo
sinfo -R
sbatch --gres=gpu:1 --wrap='nvidia-smi'
squeue

sudo scontrol update NodeName=$HOST State=RESUME
sinfo
squeue
驗收：看到 Pending job 時，不是只知道「沒跑」。你會先看 squeue reason、sinfo -R、node state、GRES 與 daemon/log。

Lab 7 — Kubernetes：先練操作與故障排除

第一週末不用為了「一定要在 K8s 裡跑 GPU」把時間全部花在 GPU Operator。先把 Kubernetes workload lifecycle 與 troubleshooting 練熟；GPU Operator / device plugin 排到 Week 2。

K3s 單機快速環境

curl -sfL https://get.k3s.io | sh -
sudo k3s kubectl get nodes

sudo k3s kubectl create deployment web --image=nginx:alpine
sudo k3s kubectl get deployments
sudo k3s kubectl get pods -o wide

sudo k3s kubectl scale deployment web --replicas=3
sudo k3s kubectl get pods

故意做出 ImagePullBackOff

sudo k3s kubectl create deployment broken --image=nginx:this-tag-does-not-exist
sudo k3s kubectl get pods

# 找到 broken pod 後
sudo k3s kubectl describe pod <POD>
sudo k3s kubectl logs <POD>
sudo k3s kubectl get events --sort-by=.lastTimestamp
kubectl get ↓ kubectl describe ↓ kubectl logs ↓ kubectl get events ↓ Config / Image / Resource / Node / Runtime
肌肉記憶：get → describe → logs → events。先用 observable evidence 定位，不要第一秒就 Google error string。

Lab 8 — MIG：第一週末先確認，不強求實機

MIG 可把支援的 NVIDIA GPU 分割成隔離的 GPU instances。是否能在 cloud VM 實際 configure，取決於 GPU 型號與 cloud provider 權限。

nvidia-smi --query-gpu=name,mig.mode.current --format=csv
nvidia-smi -L
Physical GPU ↓ Enable MIG GPU Instance (GI) ↓ Compute Instance (CI) ↓ CUDA workload / scheduler resource

真正租到支援 MIG 且 provider 允許管理的 GPU 後，再依 NVIDIA MIG User Guide 操作 nvidia-smi -mig 與 nvidia-smi mig。不要在不支援的 VM 上把權限限制誤判成自己 command 不會下。

6. Base Command Manager（BCM）— Professional 等級的核心

不要混淆：這裡的 BCM = Base Command Manager，不是 BMC = Baseboard Management Controller。
Base Command Manager │ ├─ Provision / software images ├─ Node categories / configuration ├─ Cluster health / monitoring / reports ├─ Users / roles / permissions ├─ Network / DPU / switch settings ├─ Slurm / Kubernetes integration └─ Troubleshooting │ ┌───────┴────────┐ ▼ ▼ Compute Nodes GPU Nodes │ │ BMC/OOB nvidia-smi / DCGM

BCM 11 可用於 cluster provisioning、workload management 與 infrastructure monitoring；官方目前提供 free-license option（每 system 最多 8 accelerators，cluster node 數不限，free license 不含 enterprise support，申請需符合官方資格）。

Week 2 的 BCM 目標

  • 完成官方 Base Command Manager Administration 課程。
  • 理解 head node、software image、node category、compute node、Base View、cmsh。
  • 能在 cmsh 查 device / node 狀態與設定。
  • 理解 BCM 如何 install / integrate Slurm、Kubernetes。
  • 練「add node → provision → verify → scheduler 看得到」的完整流程；若自己的 cloud 環境無法重現，使用 NVIDIA 官方 lab / course environment 補足。
為什麼不能只學 Slurm：Slurm 重點是 job scheduling；BCM 的 scope 是整個 cluster lifecycle。NCP-AIO blueprint 對 BCM 的要求包含 monitoring、resource/node health、patch/firmware/software image、users/roles、network、node categories、Kubernetes/Slurm 安裝與 cluster troubleshooting。

  • NVLink / NVSwitch / Fabric Manager：scale-up fabric 與 service troubleshooting。

Week 4 Drill 範例

Slurm
Node 被 drain、GRES 數不對、job pending。要求：10 分鐘內找到 reason，修復並讓 job 跑起來。
Kubernetes
ImagePullBackOff、resource request 無法滿足、node NotReady。要求：用 get/describe/logs/events 找 evidence。
NGC/Docker

BCM

Fabric / Storage能把低 GPU util / distributed training slowdown 往 network、NVLink/NVSwitch、storage、Magnum IO 做系統性定位。
Timed practice在 120 分鐘壓力下完成混合 MCQ + 3 個 lab-style scenarios，不靠 Google 才能走完核心流程。
Go / No-Go：BCM、Slurm、Kubernetes 三個只要有一個還停留在「我知道它是什麼，但 command 不熟」，就先不要報。
