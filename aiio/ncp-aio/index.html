4. 2026-08-22 A100 真實實戰紀錄

實測這一節不是理論範例：以下流程已在 Brev 的 hyperstack_A100_80G 實際操作過。GI/CI ID、MIG UUID、價格與 provider capacity 都可能在下次建立 instance 時改變，不能硬背。

4.1 今天實際打通的 end-to-end path

Mac │ ├─ brev search / create ▼ Brev GPU VM A100 80GB PCIe Driver 570.195.03 CUDA Driver API 12.8 │ ├─ PyTorch cu128 ├─ Full GPU load → nvidia-smi │ ├─ MIG Enabled │ └─ GI 1g.10gb → CI → MIG UUID │ ├─ DCGM 4.6.1 │ └─ MIG sm_active / occupancy / DRAM activity │ ├─ NVIDIA Container Toolkit / CDI │ └─ refresh after MIG reconfiguration │ └─ NGC PyTorch 25.03 container └─ CUDA 12.8 / MIG 1g.10gb / ~9.5 GiB visible 收尾：brev delete → brev list → No instances

4.2 今天遇到的錯誤，反而是最有價值的教材

現象真正原因解法 / 學到什麼
torch.cuda.is_available() == False，警告 driver 太舊、found version 12080Host driver API 支援 CUDA 12.8，但原 PyTorch build 比 host driver 所能支援的 CUDA 新。不要先亂升 cloud VM driver；改用與 driver 相容的 PyTorch CUDA 12.8 build（cu128）或 NGC 25.03。
MIG Enabled 後 PyTorch 又變 False只有開 MIG mode，尚未建立 GI + CI，因此沒有可供 CUDA 使用的 MIG device。建立 GI/CI；理解「MIG mode」與「可用 MIG CUDA device」是兩件事。
nvidia-smi 在 MIG mode 顯示 GPU-Util N/AA100 MIG 下，傳統 physical GPU utilization 顯示不等於 individual MIG profiling。改用 DCGM profiling 看 MIG entity。
apt-get install dcgmi 找不到 packagedcgmi 是 DCGM 套件裡的 CLI，不是 Ubuntu package 名稱。安裝 datacenter-gpu-manager-4-cuda12，啟動 nvidia-dcgm。
Docker 指定 MIG UUID 出現 unresolvable CDI devicesMIG reconfiguration 後 CDI spec 還是舊 inventory。sudo systemctl restart nvidia-cdi-refresh.service 後重新 nvidia-ctk cdi list。
CDI device 名稱變成 nvidia.com/gpu=nvidia.com/gpu=...變數本身已經包含 CDI prefix，又在 command 前面重加一次。MIG_UUID 只存純 MIG-... UUID；CDI prefix 只組一次。
docker run --rm ubuntu nvidia-smi 找不到 executable普通 Ubuntu container 沒有 GPU injection / driver utility exposure。比較有無 --gpus all，理解 Container Toolkit 的角色。
按 Ctrl+C 離開 brev create waiting只停止本地 CLI 等待，不會自動刪除已成功建立的 instance。一定要 brev list 看 final state；不用就 brev delete。

5. NVIDIA Brev：租 GPU、provider、計費與安全收尾

Brev 把多個 cloud provider 的 GPU instances 放到同一套 search / create / shell / lifecycle CLI 裡。PROVIDER 不同很正常；同樣 A100 的 CPU、disk、region、feature、price、availability 都可能不同。

5.1 macOS 安裝與登入

brew install brevdev/homebrew-brev/brev
brev --version
brev login

5.2 先 search，不要急著 create

# 由低價到高價
brev search --sort price

# 只看 A100 / H100
brev search --gpu-name A100 --sort price
brev search --gpu-name H100 --sort price

# 只看可 stop 的 instance
brev search --stoppable --sort price
欄位怎麼讀
TYPE建立 instance 時可以直接給 --type 的 instance type。
PROVIDER實際 capacity 的 provider label，例如 GCP、AWS、Crusoe 或 hyperstack:shadeform。不要假設所有 provider 的 VM feature 一樣。
GPU / COUNT / VRAMGPU 型號、張數、單卡與總 VRAM。
CAPABILITYCompute Capability，例如 A100 是 8.0、H100 是 9.0。
DISK / $/GB/MO磁碟大小與 Brev search 是否另外顯示 storage rate；若是 -，不要自行杜撰每 GB 價格，到 Billing 看實際 usage。
FEATURESS=stoppable、R=rebootable、P=flex ports；- 表示沒有這些 advertised features。
$/HR當下 search 顯示的 running compute hourly rate；價格會變。

5.3 今天為什麼選 A100 而不是 H100

8/22 當下 search 最低價大約：

實例GPU當時價格用途判斷
hyperstack_A100_80GA100 80GBUS$1.62/hr支援 MIG，足以完成今天所有 lab。
hyperstack_H100H100 80GBUS$3.00/hr更高階，但今天學 MIG/DCGM/NGC 不需要多付接近一倍。
價格是 2026-08-22 當下觀察，不是固定價目表。每次建立前都重新 brev search --sort price。

5.4 Dry-run 與真正建立

# 只預覽，不建立
brev create nca-a100 \
  --type hyperstack_A100_80G \
  --dry-run

# 真正建立
brev create nca-a100 \
  --type hyperstack_A100_80G
關鍵：--dry-run 不建立 instance；真正 create 成功後，即使你在「Waiting for instance(s) to be ready」按 Ctrl+C，已建立的 instance 仍可能繼續 provisioning / running。立刻用 brev list 驗證。

5.5 計費模型怎麼想

Brev Organization Credit Balance │ Running instance │ compute $/hour │ （可能另有 storage） Stopped（僅支援 S 的 instance） → 無 compute charge → storage 可能繼續計費 Deleted → instance 與資料永久刪除 → 該 instance 不再計費

Brev Console 的 Billing 可看 compute / storage usage、credit balance、burn rate、payment method 與 Auto Recharge。若你沒有自己輸入卡但 instance 能建立，應直接以 Organization Billing / Credits 為準，不要猜是不是「免費」。

5.6 Hyperstack A100 的 storage 要怎麼看

今天 hyperstack_A100_80G 的 search 顯示約 850GB disk，而 $/GB/MO 是 -。這代表 CLI 沒有提供一個可讓你用「850 × $x/GB/月」直接計算的 storage rate。不要自行假設它等於 0 或某個 GCP/AWS 價格；最準的是 Billing → Usage。

5.7 今天安全收尾的標準 SOP

# VM 內：先保存重要內容
git status
git push   # 若有需要

# 回到 Mac
exit

brev list
brev delete nca-a100

# 最後一定再確認
brev list
今天最終驗證：brev list 顯示 No instances in org ...。這才是「今天不再讓 A100 繼續跑」的最終確認；exit、Ctrl+C 都不是 billing stop。

Lab 2 — PyTorch / CUDA 相容性與 GPU Load

6.2.1 今天第一個實際錯誤：PyTorch build 太新

一開始執行：

python3 ~/workspace/gpu_load.py

得到：

UserWarning: CUDA initialization:
The NVIDIA driver on your system is too old (found version 12080)
...
assert torch.cuda.is_available()
AssertionError

12080 對應 CUDA Driver API 12.8。Host 是 R570 / CUDA 12.8，問題不是 A100 壞掉，而是 Python 環境中的 PyTorch CUDA build 與 host driver 不相容。

建議解法：不要先亂升 cloud driver，建立乾淨 cu128 venv

python3 -m venv ~/nca-env
source ~/nca-env/bin/activate
python -m pip install --upgrade pip

python -m pip install torch torchvision torchaudio \
  --index-url https://download.pytorch.org/whl/cu128

python - <<'PY'
import torch
print("PyTorch:", torch.__version__)
print("PyTorch CUDA:", torch.version.cuda)
print("CUDA available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("GPU:", torch.cuda.get_device_name(0))
PY

製造 compute-heavy workload

cat > ~/workspace/gpu_load.py <<'PY'
import torch, time
assert torch.cuda.is_available()
print("GPU:", torch.cuda.get_device_name(0))
a = torch.randn(4096, 4096, device="cuda")
b = torch.randn(4096, 4096, device="cuda")
end = time.time() + 60
count = 0
while time.time() < end:
    c = torch.matmul(a, b)
    torch.cuda.synchronize()
    count += 1
print("Iterations:", count)
PY

# Terminal A
python3 ~/workspace/gpu_load.py

# Terminal B
watch -n 1 nvidia-smi

今天看到什麼

IdleFull GPU workload
GPU-Util 0%、約 47–52W、無 processGPU-Util 100%、python3 process 出現、約 700MiB VRAM、power 明顯升高
重要觀念：VRAM usage ≠ GPU utilization。今天 workload 只用了不到 1GB VRAM，仍可把 compute units 打到 100%。

Lab 3 — A100 MIG：從 Physical GPU 到 GI / CI / CUDA Device

今天真正租到 A100 80GB 且 provider 允許 MIG management，因此這一節已從「概念」升級成實機 SOP。

6.3.1 Enable MIG

# 先停止 workload
pkill -f gpu_load.py || true

# 啟用 MIG
sudo nvidia-smi -i 0 -mig 1

nvidia-smi
nvidia-smi -L
最容易誤會：MIG mode = Enabled 之後，如果你還沒有建立 GI + CI，PyTorch 可能會看到 torch.cuda.is_available() == False。這不是壞掉；只是沒有可用 CUDA MIG device。

6.3.2 列出 Profile：-lgip 不是列 GI

sudo nvidia-smi mig -lgip

今天 A100 80GB 列出：

ProfileProfile ID（本次）Free/Total 起始約可用 FB memory
1g.10gb197/79.50 GiB
1g.20gb154/419.50 GiB
2g.20gb143/319.50 GiB

Free/Total = 7/7 是「7 個都還 free」，不是已經建立 7 個。

6.3.3 建立 1 個 1g.10gb GI + CI

sudo nvidia-smi mig -cgi 19 -C

本次輸出建立了 GPU Instance ID 9 與 Compute Instance ID 0；這些 ID 是 runtime 產生，不要硬背。

6.3.4 四個 command 不要混

Command看什麼
nvidia-smi mig -lgip有哪些 GPU Instance Profiles 可用、Free/Total。
nvidia-smi mig -lgi現在已建立哪些 GPU Instances (GI)。
nvidia-smi mig -lci現在已建立哪些 Compute Instances (CI)。
nvidia-smi -LPhysical GPU + 最終 CUDA 可見的 MIG device / UUID。

6.3.5 驗證 MIG CUDA device

nvidia-smi -L

python3 - <<'PY'
import torch
print("CUDA available:", torch.cuda.is_available())
print("Device count:", torch.cuda.device_count())
if torch.cuda.is_available():
    p = torch.cuda.get_device_properties(0)
    print("Device:", torch.cuda.get_device_name(0))
    print("VRAM GiB:", p.total_memory/1024**3)
PY

今天建立後可看到 MIG 1g.10gb Device 0，PyTorch workload 正常跑在 GI/CI 內，約 9.5 GiB VRAM 可見。

6.3.6 要切 5 個 1g.10gb

sudo nvidia-smi mig -dci
sudo nvidia-smi mig -dgi

# 一次建立五個 1g.10gb GI 並建立 default CI
sudo nvidia-smi mig -cgi 19,19,19,19,19 -C

6.4.3 MIG instance 即時監控

先用 dcgmi discovery -c 找 DCGM 自己的 MIG entity ID。不要把 nvidia-smi 的 GI ID 直接當作 DCGM EntityID。

dcgmi dmon \
  -e 1002,1003,1004,1005 \
  -i instance:0 \
  -d 1000

今天 gpu_load.py running 時看到大約：

#Entity   SMACT   SMOCC   TENSO   DRAMA
GPU-I 0   0.995   0.247   0.000   0.338
GPU-I 0   0.994   0.246   0.000   0.338

workload 停掉後回到接近：

GPU-I 0   0.000   0.000   0.000   0.000
這個實驗非常重要：SMACT ≈ 0.995 表示「這個 MIG instance 分到的 SM resources 幾乎一直有工作」，不是說整張 A100 99.5% utilized。SMOCC ≈ 0.247 也證明 SM 很忙不等於 occupancy 很高。

6.4.4 為什麼 nvidia-smi dmon 的 sm / mem 是 -

nvidia-smi dmon

MIG mode 下，今天仍可看到 physical GPU 的 power、temperature、mclk/pclk，但 sm / mem 顯示 -。這不是 0；是這個 view 無法提供該 MIG utilization。MIG profiling 改用 DCGM。

Lab 5 — Docker + NVIDIA GPU + CDI

6.5.1 先比較有沒有 GPU exposure

docker --version
docker info

# 有 GPU exposure
docker run --rm --gpus all ubuntu nvidia-smi

# 故意拿掉 --gpus all
docker run --rm ubuntu nvidia-smi

第二條今天得到 exec: "nvidia-smi": executable file not found in $PATH。因為普通 Ubuntu image 本來沒有 NVIDIA driver utility；--gpus all 會經 NVIDIA container stack 做 device/library exposure。

6.5.2 為什麼 MIG UUID 一開始無法給 Docker

Host 已經有：

GPU 0: NVIDIA A100 80GB PCIe
  MIG 1g.10gb Device 0: (UUID: MIG-...)

但 Docker 指定 MIG 時出現：

failed to inject CDI devices:
unresolvable CDI devices nvidia.com/gpu=MIG-...

原因是今天先 reconfigure MIG，CDI inventory 還沒 refresh。NVIDIA Container Toolkit 的 nvidia-cdi-refresh 已知不會在每次 MIG reconfiguration 自動重建 spec。

6.5.3 Refresh CDI

nvidia-ctk cdi list

sudo systemctl restart nvidia-cdi-refresh.service

nvidia-ctk cdi list

今天 refresh 前只有 physical GPU entries；refresh 後新增類似：

nvidia.com/gpu=0:0
nvidia.com/gpu=MIG-<UUID>

6.5.4 正確指定一個 MIG 給 container

# 變數只放純 MIG UUID，不要放 nvidia.com/gpu=
MIG_UUID=$(nvidia-smi -L | grep -o 'MIG-[^)]*' | head -1)
echo "$MIG_UUID"

docker run --rm \
  --runtime=nvidia \
  -e NVIDIA_VISIBLE_DEVICES="nvidia.com/gpu=${MIG_UUID}" \
  ubuntu \
  nvidia-smi -L
今天踩過的坑：如果 $MIG_UUID 自己已經是 nvidia.com/gpu=MIG-...，command 又寫 nvidia.com/gpu=$MIG_UUID，最後會變成 nvidia.com/gpu=nvidia.com/gpu=...，CDI 當然解析不到。

6.5.5 Docker 為什麼 docker ps 是空的

docker run --rm ... nvidia-smi 執行完 nvidia-smi 就退出，--rm 又自動刪 container，所以 docker ps 看不到是正常。要 interactive：

docker run --rm -it \
  --runtime=nvidia \
  -e NVIDIA_VISIBLE_DEVICES="nvidia.com/gpu=${MIG_UUID}" \
  ubuntu bash

今天成功輸出：

PyTorch: 2.7.0a0+7c8ec84d.nv25.03

能力最低標準

GPU看到 nvidia-smi / -q / topology 能快速判讀 inventory、usage、power/temp、process。
