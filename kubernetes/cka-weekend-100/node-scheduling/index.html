Node Scheduling
實戰筆記

從 node-role.kubernetes.io/control-plane 的空 value，到 Taint/Toleration、Node Affinity、YAML 縮排、kubectl explain 與 apply / replace。把剛剛容易混淆的點整理成考場可直接查用的版本。

繁體中文可列印附驗證命令

01 · Mental Model

先分清楚：誰拒絕誰、誰選擇誰

LabelNode 身上的特徵，例如 color=blue。
選擇機制nodeSelector 或 Node Affinity 要求／偏好某些 Node。
排斥機制Taint 讓 Node 拒絕沒有相符 Toleration 的 Pod。
一句話：Node Affinity 是 Pod 說「我要去哪裡」；Taint 是 Node 說「誰不能進來」；Toleration 只是取得進入資格，不保證一定排到該 Node。
Taint 語法與空 valuenodeSelector 與 TolerationRequired / Preferred Operator 速查kubectl explainYAML 除錯 apply / replace / force考場工作流命令速查

02 · Taints

key[=value]:effect 到底怎麼讀？

spray=mosquito:NoSchedule
└ key ┘ └ value ┘ └ effect ┘

node-role.kubernetes.io/control-plane:NoSchedule
└──────────────── key ───────────────┘ └ effect ┘
                     value 為空

有 value

kubectl taint node node01 \
  spray=mosquito:NoSchedule

YAML 會包含 key、value、effect。

沒有 value

kubectl taint node controlplane \
  node-role.kubernetes.io/control-plane:NoSchedule

YAML 只有 key 與 effect；省略的 value 是空字串。

常見錯誤：key=node-role.kubernetes.io/control-plane:NoSchedule- 不是「指定 key」。它會把字面上的 key 當作 taint key，把後面內容當 value。
# 精確移除 control-plane 的 NoSchedule taint
kubectl taint node controlplane node-role.kubernetes.io/control-plane:NoSchedule-

# 最後的 - 代表刪除，不是 value 的一部分
kubectl describe node controlplane | grep -i Taints

03 · Labels & Node Selection

空 label value 仍然是合法 label

metadata:
  labels:
    node-role.kubernetes.io/control-plane: ""

整段 node-role.kubernetes.io/control-plane 是 key；其 value 通常為空字串。查看與篩選：

kubectl get nodes --show-labels
kubectl get node controlplane -o jsonpath='{.metadata.labels}{"\n"}'
kubectl get nodes -l node-role.kubernetes.io/control-plane
Flag 易錯：JSONPath 必須透過輸出選項：-o jsonpath='...'，不存在獨立的 --jsonpath flag。

使用 nodeSelector

spec:
  nodeSelector:
    node-role.kubernetes.io/control-plane: ""

kubectl create deployment 沒有 --labelselector。先產生 Deployment YAML，再把 nodeSelector 放進 spec.template.spec。

Control Plane 還有 Taint 時

spec:
  nodeSelector:
    node-role.kubernetes.io/control-plane: ""
  tolerations:
  - key: node-role.kubernetes.io/control-plane
    operator: Exists
    effect: NoSchedule
兩者缺一不可：nodeSelector 選中 Control Plane；toleration 通過它的 NoSchedule 門禁。

04 · Node Affinity

Required 與 Preferred 的 YAML 結構不同

硬性條件

Required

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: color
          operator: In
          values:
          - blue

不符合就不能排程。

軟性偏好

Preferred

affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      preference:
        matchExpressions:
        - key: color
          operator: In
          values:
          - blue

優先選符合者，但必要時可選其他 Node。

為什麼 Preferred 查不到 nodeSelectorTerms？因為它根本沒有這層。Required 是 nodeSelectorTerms[]；Preferred 的每一項是 weight + preference，而 preference 本身就是一個 NodeSelectorTerm。

空值的 Control Plane label：用 Exists 最清楚

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists

05 · Operators

Node Affinity Operator 速查

Operator意義values典型用途
Invalue 在清單內必須提供color ∈ [blue, green]
NotInvalue 不在清單內必須提供排除 test 節點
Existskey 存在即可不可提供空 value 的角色 label
DoesNotExistkey 不存在不可提供排除具有某角色的 Node
Gt數值大於指定值一個整數字串自訂數值 label
Lt數值小於指定值一個整數字串自訂數值 label
沒有 Equal：Node Affinity 不支援 operator: Equal。精確比對請用 In 加單一 value；只檢查 key 則用 Exists。

06 · API Discovery

忘記欄位時，沿著 FIELDS 一層層查

# Required：經過 nodeSelectorTerms
kubectl explain pod.spec.affinity.nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution
kubectl explain pod.spec.affinity.nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution.nodeSelectorTerms
kubectl explain pod.spec.affinity.nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution.nodeSelectorTerms.matchExpressions.operator

# Preferred：經過 preference，不經過 nodeSelectorTerms
kubectl explain pod.spec.affinity.nodeAffinity.preferredDuringSchedulingIgnoredDuringExecution
kubectl explain pod.spec.affinity.nodeAffinity.preferredDuringSchedulingIgnoredDuringExecution.preference
kubectl explain pod.spec.affinity.nodeAffinity.preferredDuringSchedulingIgnoredDuringExecution.preference.matchExpressions.operator

看到 <[]PreferredSchedulingTerm> 代表它是陣列，但 explain 路徑不需要填 [0]。直接從輸出的 FIELDS 選下一個欄位名稱。

# 一次展開整個子樹
kubectl explain pod.spec.affinity.nodeAffinity --recursive

07 · YAML Debugging

解析錯誤通常先看縮排，不要先懷疑 Kubernetes

錯誤

template:
  spec:
      affinity:       # 縮排過深
        ...
    containers:       # 同層卻不一致

常見錯誤：did not find expected key。

正確

template:
  spec:
    affinity:
      ...
    containers:
    - name: nginx

affinity 與 containers 都是 Pod spec 的直接子欄位。

  • affinity 必須放在 spec.template.spec.affinity，不是 Deployment 的最外層 spec.affinity。
  • 空字串明確寫成 ""；只留下冒號會解析成 YAML null。
  • nodeSelector 與 required Node Affinity 若表達相同條件，保留一種即可。
  • operator: Exists 不要加 values。
# 第一關：本機解析與基本結構
kubectl apply -f red.yaml --dry-run=client

# 第二關：交給 API Server 驗證，但不保存
kubectl apply -f red.yaml --dry-run=server

# 顯示行號，快速定位錯誤
nl -ba red.yaml | sed -n '25,45p'

08 · Updating Resources

apply、replace、replace --force

命令核心行為是否刪除重建常見輸出
kubectl apply -f blue.yaml宣告式合併期望狀態否configured / unchanged
kubectl replace -f blue.yaml以檔案提供完整規格進行更新否replaced
kubectl replace --force -f blue.yaml先 DELETE，再 CREATE 同名資源是deleted + replaced
語法錯誤：使用 -f 時，不要再加入 resource argument。正確是 kubectl replace -f blue.yaml，不是 kubectl replace deploy -f blue.yaml。

對 Deployment，實務上 replace 可能在輸入 YAML 沒有 resourceVersion 時仍成功，代表伺服器接受該次無條件更新；不要因此把它當成所有資源都保證相同。若 YAML 來自 kubectl get ... -o yaml，帶著目前的 resourceVersion 可提供 optimistic concurrency 檢查。

# 產生「新建模板」：沒有 live resourceVersion
kubectl create deploy blue --image=nginx --replicas=3 \
  --dry-run=client -o yaml > blue.yaml

# 匯出目前 live object：通常包含 resourceVersion
kubectl get deploy blue -o yaml > blue.yaml

09 · Exam Workflow

考場可靠流程：生成、編輯、驗證、套用、查結果

  1. 先看 Node label 與 taint：kubectl get nodes --show-labels、kubectl describe node ...。
  2. 用 imperative command 生成骨架：kubectl create deployment ... --dry-run=client -o yaml。
  3. 把 affinity / nodeSelector / tolerations 放到 spec.template.spec。
  4. 不確定 schema 就用 kubectl explain，不要憑印象創造欄位或 operator。
  5. 先跑 client dry-run，再跑 server dry-run。
  6. 正式套用後，以實際 Pod 所在 Node 驗收。
kubectl apply -f red.yaml --dry-run=client
kubectl apply -f red.yaml --dry-run=server
kubectl apply -f red.yaml
kubectl rollout status deploy/red
kubectl get pods -l app=red -o wide
kubectl describe pod <pod-name> | sed -n '/Events:/,$p'

10 · Quick Reference

最後 60 秒速查

# 加 label
kubectl label node node01 color=blue --overwrite

# 加／移除 taint
kubectl taint node node01 spray=mosquito:NoSchedule
kubectl taint node node01 spray=mosquito:NoSchedule-

# 找有 control-plane label 的 Node
kubectl get nodes -l node-role.kubernetes.io/control-plane

# 看 Pod 排到哪裡
kubectl get pods -o wide

# 忘記 Node Affinity schema
kubectl explain pod.spec.affinity.nodeAffinity --recursive

# 安全驗證 manifest
kubectl apply -f manifest.yaml --dry-run=server

完成檢查

  • 我能指出 taint 的 key、value、effect。
  • 我知道最後的 - 是移除 taint。
  • 我能解釋 Affinity 與 Toleration 的角色差異。
  • 我記得 Required 走 nodeSelectorTerms，Preferred 走 weight + preference。
  • 我會用 kubectl explain 找 operator。
  • 我知道 replace --force 是 delete + create。
