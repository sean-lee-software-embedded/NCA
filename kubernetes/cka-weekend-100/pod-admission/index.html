02 · Pod Updates

現有 Pod 大多不是「改」，而是「重建」

Pod 的許多規格欄位不可原地更新。最安全的考場心法是：先看 ownerReferences；若由 Deployment 等控制器管理，就修改控制器的 Pod template，讓它建立新 Pod。

變更一般更新是否可行正確做法／注意
spec.containers[*].image
spec.initContainers[*].image		可以kubectl set image pod/...；有 owner 時仍優先改 Deployment。
spec.activeDeadlineSeconds可以受 API 驗證規則約束；用 server dry-run 先驗證。
spec.tolerations只可新增既有 toleration 不能任意刪除或改寫。
spec.terminationGracePeriodSeconds
spec.schedulingGates		有限制地可改前者有特定例外；後者只能移除既有 gate。以題目版本的 kubectl explain 與 server dry-run 為準。
CPU / memory requests、limits視版本與功能而定In-place Pod resize 走 resize subresource；不要把它當一般 kubectl edit pod 保證可用。
env、command / args、ServiceAccount、volumes、多數排程欄位不可以改 owner template，或刪除並重建 standalone Pod。
kubectl replace --force 不是神奇更新：它會先 DELETE 再 CREATE。同名不代表同一個 Pod；UID、IP 可能改變，也可能有停機空窗。
# 先判斷 owner；kind/name 為空代表 standalone Pod
kubectl get pod web -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'

# 有 Deployment owner：修改 Deployment，而非子 Pod
kubectl set image deployment/web web=nginx:1.27
kubectl rollout status deployment/web

# standalone Pod：先保留乾淨規格，再依題意重建
kubectl get pod web -o yaml > /tmp/web.yaml
# 編輯時移除 status 與 server-managed metadata
kubectl replace --force -f /tmp/web.yaml

03 · Controllers

ReplicaSet 和 DaemonSet：都是補 Pod，但「補到多少」不同

比較ReplicaSetDaemonSet
目標整個叢集維持指定的副本總數每個符合條件的 Node 各維持一個 Pod
Pod 數來源spec.replicaseligible Node 數量；沒有 replicas
Node 新增／移除不一定改變副本數自動在新 Node 建立、Node 消失時清理
典型用途Web / API 等可水平擴展工作負載log、monitoring、CNI、CSI 等 node agent
平常由誰管理通常由 Deployment 建立與管理直接管理其 Pod

ReplicaSet 判斷句

「我需要總共 N 個。」Pod 可分散，也可能集中；要控制分散需另外使用 topology spread、affinity 等排程機制。

kubectl get deploy,rs,pod -o wide
kubectl describe rs <name>

DaemonSet 判斷句

「每個符合資格的 Node 都要一個。」DESIRED=0 可能只是 selector、affinity 或 taint 讓所有 Node 都不符合。

kubectl get ds -A -o wide
kubectl describe ds <name> -n <ns>

04 · Static Pods

Static Pod 是 kubelet 的本機工作，不經 scheduler

比較Static PodRegular Pod
建立與管理者特定 Node 的 kubeletAPI Server 接收物件；controller / scheduler / kubelet 協作
來源kubelet 的 staticPodPath；kubeadm 常為 /etc/kubernetes/manifestskubectl、controller 或其他 API client
是否排程否，天生綁定該 Node通常由 scheduler 選 Node
API 中可見性kubelet 建立唯讀的 mirror Pod，名稱通常加 Node 名完整 API 物件
如何真正刪除移除／修改 Node 上的 manifest；只刪 mirror Pod 無效刪 API 物件或修改 owner
可否引用 API 物件不能引用 ServiceAccount、ConfigMap、Secret 等 API 物件可以
為何控制平面適合：即使 API Server 尚未啟動，kubelet 仍可從本機 manifest 啟動 kube-apiserver、etcd、controller-manager 與 scheduler。
不要把備份留在 manifest 目錄：kubelet 會掃描目錄內所有非點檔，不依副檔名判斷。把 .bak 放在裡面仍可能被讀取。
# 確認實際 staticPodPath，不要只背預設路徑
sudo grep -n 'staticPodPath' /var/lib/kubelet/config.yaml
sudo ls -la /etc/kubernetes/manifests

# API 可用時看 mirror Pod；Node 上直接看 runtime / kubelet
kubectl get pods -A -o wide | grep "$(hostname)"
sudo crictl ps -a
sudo journalctl -u kubelet --since '10 min ago' --no-pager

05 · Manifest Debugging

範例 static-busybox.yaml 錯在哪裡？

原檔看起來像把 kubectl get pod -o yaml 的結果直接存回 manifest 目錄。它同時有「不能放進 Static Pod 的 API 依賴」與「command 寫法錯誤」。

原內容問題修法
creationTimestamp、generation、resourceVersion、uid、statusAPI Server 管理的輸出欄位，不是可攜式宣告規格刪除；manifest 只留必要 metadata 與 spec
serviceAccountName 與 kube-api-access-... projected volume自動注入的 API 物件依賴；Static Pod 不支援移除 ServiceAccount volume 與 volumeMount
command: ["sleep 1000"]Kubernetes 會找一個字面名稱為 sleep 1000 的 executablecommand: ["sleep"]、args: ["1000"]
args: ["dry-run=client"]--dry-run=client 是 kubectl flag，卻誤成 container argumentflag 放在 kubectl 指令；不要放 Pod spec

最小正確版本

apiVersion: v1
kind: Pod
metadata:
  name: static-busybox
  namespace: default
spec:
  containers:
  - name: static-busybox
    image: busybox:1.36
    command: ["sleep"]
    args: ["1000"]
  restartPolicy: Always

用 kubectl 產生乾淨骨架

kubectl run static-busybox --image=busybox:1.36 --restart=Always \
  --dry-run=client -o yaml --command -- sleep 1000 \
  > /tmp/static-busybox.yaml

# 先在 manifest 目錄外檢查，再移入
kubectl apply --dry-run=client -f /tmp/static-busybox.yaml
sudo mv /tmp/static-busybox.yaml /etc/kubernetes/manifests/
sudo crictl ps -a | grep static-busybox
sudo journalctl -u kubelet --since '5 min ago' --no-pager | grep -i static-busybox

06 · Admission Controllers

它是「寫入 API」的最後門禁與加工站

Authentication你是誰？
Authorization你能做嗎？
Mutating補值／修改，也可拒絕
Validating只判斷接受或拒絕
Persist通過後寫入 etcd
順序要記：Mutation 在 Validation 之前。因此驗證看到的是已經被預設或修改過的物件。Admission 主要處理 CREATE、UPDATE、DELETE、CONNECT 等寫入／特殊請求；讀取用的 GET、LIST、WATCH 不經 Admission。
類型能做什麼常見例子
Mutating admission修改／補預設值，也能拒絕DefaultStorageClass、DefaultTolerationSeconds、ServiceAccount、LimitRanger
Validating admission檢查後接受或拒絕，不能修改NamespaceLifecycle、ResourceQuota、PodSecurity、NodeRestriction
Admission webhookAPI Server 呼叫外部 HTTPS 服務MutatingWebhookConfiguration、ValidatingWebhookConfiguration
Admission policy以 CEL 在 API Server 內表達規則ValidatingAdmissionPolicy；較新版本另有 MutatingAdmissionPolicy，考場以版本文件為準

這也解釋了為何從一般 Pod 匯出的 YAML 會看到自己沒寫的 ServiceAccount token volume 與 not-ready／unreachable tolerations：它們可能來自 API 預設與 Admission；不能原封不動搬去 Static Pod。

# kubeadm control plane：檢查 API Server flags
sudo grep -n -- '--.*admission' /etc/kubernetes/manifests/kube-apiserver.yaml

# flag 中沒列出，不代表預設 plugin 沒啟用
# 修改前保留 NodeRestriction，並以該版本官方文件核對預設集合
--enable-admission-plugins=NodeRestriction,NamespaceAutoProvision
--disable-admission-plugins=AlwaysPullImages

# 找動態 webhook 與 CEL policy
kubectl get mutatingwebhookconfigurations,validatingwebhookconfigurations
kubectl get validatingadmissionpolicies,validatingadmissionpolicybindings 2>/dev/null || true

NamespaceLifecycle

保護 namespace 生命週期，例如拒絕在正在終止的 namespace 建立資源；它不會自動替你建 namespace。

NamespaceAutoProvision

請求使用不存在的 namespace 時可自動建立；不要和 NamespaceLifecycle 混為一談。

07 · Exam Workflow

從症狀定位到責任層

  1. 先確認 context 與 namespace：kubectl config current-context、kubectl config view --minify。
  2. 建立時立即報錯：讀 API 回應，優先查 schema、RBAC、Admission、quota。
  3. 物件已存在但 Pending：看 scheduler events、Node label / taint、requests。
  4. 已排到 Node 卻起不來：看 container status、logs、kubelet 與 runtime。
  5. 資源會自動補回：先查 owner/controller，不要一直刪子 Pod。
  6. 是 Static Pod：登入該 Node，查 manifest、crictl、kubelet journal。
kubectl get pod <pod> -o wide
kubectl describe pod <pod>
kubectl get pod <pod> -o jsonpath='{.metadata.ownerReferences}{"\n"}'
kubectl get events --sort-by=.metadata.creationTimestamp | tail -30
kubectl logs <pod> -c <container> --previous
kubectl apply --dry-run=server -f manifest.yaml

完成檢查

  • 我知道 env / ServiceAccount 不能直接改現有 Pod，應改 owner template 或重建。
  • 我能用「總共 N 個」和「每 Node 一個」分辨 ReplicaSet / DaemonSet。
  • 我知道 mirror Pod 可見，但刪 mirror Pod 不會停止 Static Pod。
  • 我能指出 static-busybox 的 command 與 ServiceAccount volume 問題。
  • 我記得 Mutating 在 Validating 之前，而且 GET / LIST / WATCH 不經 Admission。
