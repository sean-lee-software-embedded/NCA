03 · ROCm Mental Model

ROCm 到底是什麼？

把 ROCm 想成 AMD 的 GPU software platform，而 HIP 是其中最核心的 GPU programming API + kernel language。框架、數學函式庫、編譯器、runtime、debug/profiling 工具共同構成完整開發環境。

PyTorch / TensorFlow / JAX / Applications
↓
MIOpen · rocBLAS · RCCL · rocFFT · rocRAND · rocSPARSE
↓
HIP Runtime + HIP Kernel Language
↓
hipcc / amdclang++ · ROCr / Driver
↓
AMD Instinct / Radeon GPU
不要背「ROCm = CUDA」就結束。比較準確的說法是：ROCm 是整個平台；HIP 對應的是 CUDA programming/runtime 層的核心開發體驗。

05 · HIP Fundamentals

這是整份教材最重要的一章

1. Host 與 Device

Host = CPU，負責配置記憶體、搬資料、launch kernel、同步；Device = GPU，大量平行執行 kernel。

2. Grid / Block / Thread

Grid
├─ Block 0
│  ├─ Thread 0
│  ├─ Thread 1
│  └─ ...
├─ Block 1
│  ├─ Thread 0
│  └─ ...
└─ ...

最常見的一維 global index：

int i = blockIdx.x * blockDim.x + threadIdx.x;

意思不是「第幾個 block」或「thread 數量」，而是：這個 thread 在整個一維工作範圍中的 global index。

3. 一個完整 vector add

#include <hip/hip_runtime.h>
#include <iostream>

__global__ void vectorAdd(const float* a,
                          const float* b,
                          float* c,
                          int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

int main()
{
    const int n = 1024;
    const size_t bytes = n * sizeof(float);

    float *h_a = new float[n];
    float *h_b = new float[n];
    float *h_c = new float[n];

    for (int i = 0; i < n; ++i) {
        h_a[i] = i;
        h_b[i] = 2 * i;
    }

    float *d_a, *d_b, *d_c;
    hipMalloc(&d_a, bytes);
    hipMalloc(&d_b, bytes);
    hipMalloc(&d_c, bytes);

    hipMemcpy(d_a, h_a, bytes, hipMemcpyHostToDevice);
    hipMemcpy(d_b, h_b, bytes, hipMemcpyHostToDevice);

    const int blockSize = 256;
    const int gridSize = (n + blockSize - 1) / blockSize;

    hipLaunchKernelGGL(vectorAdd,
                       dim3(gridSize),
                       dim3(blockSize),
                       0, 0,
                       d_a, d_b, d_c, n);

    hipDeviceSynchronize();

    hipMemcpy(h_c, d_c, bytes, hipMemcpyDeviceToHost);

    std::cout << h_c[10] << "\n";

    hipFree(d_a);
    hipFree(d_b);
    hipFree(d_c);
    delete[] h_a;
    delete[] h_b;
    delete[] h_c;
}

4. 六個 API 先做到秒答

API用途你要立刻想到
hipMalloc()配置 device memoryGPU memory allocation
hipMemcpy()host/device 之間拷貝方向參數很重要
hipMemcpyHostToDeviceCPU → GPUinput upload
hipMemcpyDeviceToHostGPU → CPUresult download
hipDeviceSynchronize()等待先前 device work 完成kernel launch 通常是 asynchronous
hipFree()釋放 device memoryresource cleanup

5. 為什麼要 if (i < n)？

grid 通常向上取整。例如 n=1000、blockSize=256，會 launch 1024 個 threads。最後 24 個 thread 如果沒有 boundary check，就可能存取陣列範圍外。

必背流程： hipMalloc → H2D hipMemcpy → kernel launch → synchronize（需要時）→ D2H hipMemcpy → hipFree。

06 · CUDA → HIP Porting

不要只會字串替換，要知道 porting pattern

CUDAHIP / ROCm概念
cudaMallochipMallocDevice allocation
cudaMemcpyhipMemcpyMemory copy
cudaFreehipFreeFree device memory
cudaDeviceSynchronizehipDeviceSynchronizeDevice synchronization
cudaStream_thipStream_tAsynchronous stream
cudaError_thipError_tError handling

HIPIFY 是什麼？

HIPIFY 協助把 CUDA source/API calls 轉成 HIP 對應形式。常見兩種：

  • hipify-clang：利用 Clang front-end / AST，語意理解與診斷能力較強。
  • hipify-perl：較輕量，偏 pattern-based conversion，環境要求低但理解力較弱。
陷阱：HIPIFY ≠ 保證 port 完就自動有最佳效能。沒有對等 library、architecture-specific code、inline PTX、CUDA 特有 feature 等，都可能需要人工修改與重新 profiling。

Porting 問題的思考順序

1. API 能不能直接 mapping？
2. Library 有沒有 ROCm 對應？
3. CUDA-specific feature 是否需要重寫？
4. Compile 是否成功？
5. Correctness 是否一致？
6. 最後才做 performance tuning。

為什麼 library awareness 很重要？

如果需求本來就是 GEMM、convolution、FFT、collective communication，通常先用成熟 ROCm library，而不是手寫低階 kernel。Library 會替你處理大量 architecture-specific optimization。

PyTorch on ROCm 的超常見陷阱

import torch

print(torch.cuda.is_available())
print(torch.cuda.get_device_name(0))
print(torch.version.hip)

在 ROCm 版 PyTorch 裡，GPU access 仍大量沿用 torch.cuda namespace。不要看到 AMD GPU 就想當然寫成不存在的 torch.amd 或 torch.rocm.is_available()。

先判斷問題類型，再選工具

你想知道什麼工具第一印象

基本指令

rocminfo
amd-smi
rocprofv3 --help
rocgdb ./vector_add

考題判讀技巧

  • 問「device inventory / architecture」：先想 rocminfo。
  • 問「temperature / power / utilization」：先想 AMD SMI。
  • 問「哪個 kernel 慢、runtime timeline」：先想 profiler。
  • 問「breakpoint、stack、source debug」：先想 ROCgdb。
版本提醒：舊教材可能看到 rocprof / rocprofv2。目前 ROCm 文件主推 rocprofv3 / ROCprofiler-SDK；考試若出現舊名稱，仍要知道它屬於 profiling 類別。

09 · Performance Fundamentals

Associate 不必鑽太深，但 practical task 要有基本效能直覺

現象先懷疑基本方向
GPU utilization 很低工作量太小、launch overhead、occupancy、CPU bottleneck看 profiler，不要先猜。
一直 H2D / D2H copyTransfer overhead能留在 device 的資料盡量留在 device。
記憶體讀取效率差Access pattern考慮 coalesced / aligned access。
Occupancy 很低Registers / LDS / block sizing 等資源限制分析限制因子，但不要把 100% occupancy 當唯一目標。
AI workload throughput 不佳Precision / library / kernel efficiency評估 FP16/BF16、optimized libraries，並驗證數值正確性。
重要陷阱：Maximum occupancy 不等於 maximum performance。真正 KPI 是 application performance / latency / throughput / correctness。

13 · Mock Exam

25 題原創模擬題

先作答再展開答案。目標不是背選項，而是能說出「為什麼其他選項錯」。

Q1. ROCm Certified Associate 官方 competency domain 不包含下列哪一項？ A. HIP fundamentals B. Porting patterns C. Multi-node architecture-aware scaling D. Profiling/debugging fundamentals
答案 C。Multi-node、architecture-aware deep tuning 比較接近 Professional / Expert；Associate 公開 domain 是 build/dependency、HIP、porting、libraries、profiling/debugging。
Q2. ROCm stack 中最核心的 C++ GPU programming API + kernel language 是？ A. MIOpen B. HIP C. RCCL D. AMD SMI
答案 B：HIP。
Q3. blockIdx.x * blockDim.x + threadIdx.x 最常代表什麼？ A. GPU id B. global thread index C. block count D. memory size
答案 B。一維 kernel 中用它把 block 內 thread index 展開成整體 global index。
Q4. 哪個 API 配置 GPU device memory？ A. hipMemcpy B. hipMalloc C. hipFree D. hipDeviceSynchronize
答案 B：hipMalloc。
Q5. hipMemcpyHostToDevice 的方向是？ A. GPU→CPU B. CPU→GPU C. GPU→GPU only D. CPU→CPU
答案 B。
Q6. hipDeviceSynchronize() 最主要的語意？ A. 編譯 kernel B. 等待先前 device work 完成 C. 配置記憶體 D. 查 GPU 溫度
答案 B。Kernel launch 通常 asynchronous，同步 API 讓 host 等 device work。
Q7. n=1000、blockSize=256 時，為什麼 kernel 常要 if(i<n)？
答案：grid 向上取整會 launch 1024 threads；最後多出的 threads 必須避免 out-of-bounds access。
Q8. 哪個工具用於協助 CUDA source 移植到 HIP？ A. ROCgdb B. HIPIFY C. MIOpen D. RCCL
答案 B：HIPIFY。
Q9. 關於 HIPIFY，哪個說法正確？ A. 轉完一定最佳化 B. 能保證所有 CUDA feature 1:1 C. 可協助 API/source conversion，但仍可能需人工修正與 tuning D. 只能做 profiling
答案 C。
Q10. CUDA cudaMalloc() 最直接的 HIP 對應？
答案：hipMalloc()。
Q11. cuDNN 對應到 ROCm 哪個 deep-learning primitive library？ A. MIOpen B. RCCL C. rocRAND D. rocFFT
答案 A：MIOpen。
Q12. Multi-GPU collective communication 最應先想到哪個 ROCm library？ A. rocBLAS B. MIOpen C. RCCL D. ROCgdb
答案 C：RCCL。NCCL ↔ RCCL 是重要 mapping。
Q13. Dense matrix / GEMM workload 最應先想到？ A. rocBLAS B. rocRAND C. ROCgdb D. AMD SMI
答案 A：rocBLAS。
Q14. FFT workload 最相關？ A. rocFFT B. MIOpen C. RCCL D. hipify-clang
答案 A：rocFFT。
Q15. ROCm PyTorch 中常用哪個 API 判斷 GPU 是否可用？ A. torch.rocm.is_available() B. torch.cuda.is_available() C. torch.amd.ready() D. torch.hip.ready()
答案 B。ROCm 版 PyTorch 仍沿用 torch.cuda namespace 存取 GPU。
Q16. 想查看 AMD GPU agent / architecture / ROCm 可見裝置，先用？ A. rocminfo B. hipify-perl C. MIOpen D. CMake
答案 A：rocminfo。
Q17. 想看 GPU power、temperature、utilization，先用？ A. ROCgdb B. AMD SMI C. rocBLAS D. hipcc
答案 B：AMD SMI。
Q18. 想知道哪個 kernel / runtime activity 花最多時間，最佳工具類型？ A. Profiler B. Linker C. Package manager D. Text editor
答案 A。ROCm 現行工具可從 rocprofv3 / ROCprofiler-SDK 類別開始。
Q19. 想 source-level breakpoint / stack debugging，先想到？ A. ROCgdb B. RCCL C. amd-smi D. rocRAND
答案 A：ROCgdb。
Q20. 程式 compile 成功但 runtime 完全看不到 GPU。最合理第一步？ A. 重寫 kernel B. 先查 rocminfo / amd-smi 與 device access C. 換成 FFT D. 提高 occupancy
答案 B。先確認 environment / driver / device visibility，不要直接改演算法。
Q21. 程式頻繁 CPU↔GPU 小量 copy，GPU acceleration 效果不好。第一個改善方向？ A. 增加 printf B. 減少不必要的 host-device transfers C. 換 debugger D. 增加 DNS cache
答案 B。
Q22. 「Occupancy 越高，效能一定越高」是否正確？
不正確。Occupancy 是重要訊號之一，但 maximum occupancy 並不保證 maximum application performance。
Q23. 已有成熟 rocBLAS 可以做 GEMM，通常何者是較好的第一選擇？ A. 先手寫 assembly kernel B. 優先評估 rocBLAS C. 一律 CPU 計算 D. 一律 HIPIFY
答案 B。成熟 domain library 通常能提供較好的開發效率與 architecture-adaptive optimization。
Q24. hipcc: command not found 最像哪類問題？ A. Toolchain/PATH B. GPU kernel occupancy C. RCCL collective D. Numerical precision
答案 A。
Q25. Associate 最適合的學習策略？ A. 先鑽 multi-node RCCL tuning B. 先把 HIP/API mapping/library/tools + 1–3 個 lab 做熟 C. 只背 GPU 型號 D. 只做 AI theory
答案 B。它最貼近官方公開 domain 與 practical-task 方向。
