AMD GPU 先分兩條主線：CDNA 與 RDNA

ROCm 可以服務不同 AMD GPU，但硬體設計目標不一樣。Certification Module 2 先用這個差異建立後續所有觀念。

CDNARDNA
主要產品AMD InstinctAMD Radeon / workstation
主要用途Data-center AI、HPCGraphics、workstation AI、local compute
MemoryHBMGDDR
Matrix accelerationMFMA 為核心概念WMMA / graphics-oriented AI acceleration
Wavefront mental model課程以 CDNA3/4 Wave64 為主課程以 Wave32 為主
★★★★★：看到 Instinct / HBM / data-center AI / HPC，先想到 CDNA；看到 Radeon / graphics / workstation，先想到 RDNA。
版本提醒：Wave size 與硬體細節會隨 architecture 演進。考 Academy quiz 時，以該課程指定世代與用語為準；不要把「所有 AMD GPU 永遠 Wave64」當成通則。
Page 102 / 120Instinct Lineage

Instinct 世代：考的是趨勢，不是背完每個 PFLOPS

課程用 MI25/MI50 → MI100 → MI200 → MI300/325 → MI350/355 → MI400 family 的演進，說明 AI accelerator 每代都在加強 compute、memory capacity、bandwidth 與低精度支援。

GCN era → CDNA 1 → CDNA 2 → CDNA 3 → CDNA 4 → next generation vector compute → matrix acceleration → multi-die/FP64 → chiplets/FP8 → FP6/FP4 → HBM4 / next-gen fabric

最值得記的是 MI300X/MI325X/MI355X 這類資料中心 GPU 使用大容量 HBM，目的不是顯示輸出，而是把大型模型權重、KV cache、activations 與 HPC data 留在高頻寬 device memory 中。

情境題若問「為何 data-center accelerator 比 workstation GPU 更重視 HBM capacity/bandwidth」，答案通常跟大型 AI/HPC working set、memory bandwidth bottleneck、multi-GPU scaling 有關。
Page 103 / 120CU · SIMD · ALU

Compute Unit 裡的 SIMD：把 64-thread wavefront 映到硬體 lanes

課程以 CDNA3/4 mental model 說明：一個 CU 具有四個 SIMD units，每個 SIMD 有 16 lanes。可用來建立「一個 instruction 同時驅動多個 ALU 對不同資料運算」的直覺。

1 Compute Unit ├─ SIMD 0 → 16 lanes ├─ SIMD 1 → 16 lanes ├─ SIMD 2 → 16 lanes └─ SIMD 3 → 16 lanes 4 SIMD × 16 lanes = 64 arithmetic lanes (course mental model)

SIMD = Single Instruction, Multiple Data。例如同一個 ADD instruction，可以讓不同 lanes 同時計算不同 array elements。

不要混：Wavefront 是一群 threads；SIMD 是實際執行 vector instruction 的硬體引擎。Wavefront ≠ SIMD。
課程式考點：4 SIMDs / CU、16 lanes / SIMD，以及 wavefront 與 SIMD 的差異。
Page 104 / 120SPMD · SIMT · SIMD

最容易混的三個詞：SPMD、SIMT、SIMD

Term全名你要用哪個角度理解
SPMDSingle Program, Multiple DataProgrammer：很多 threads 跑同一份 kernel，各自處理不同資料
SIMTSingle Instruction, Multiple ThreadsGPU execution：一組 threads 共享執行流程、lockstep 推進
SIMDSingle Instruction, Multiple DataHardware：vector lanes 對不同 data 做相同 arithmetic
你寫 HIP kernel（SPMD） ↓ threads 被組成 wavefront（SIMT） ↓ SIMD lanes 真正做 arithmetic
★★★★★ 口訣：SPMD = 我怎麼寫；SIMT = GPU 怎麼跑 threads；SIMD = ALU 怎麼算。
Page 105 / 120Grid → Wavefront

Thread hierarchy：Grid → Block → Wavefront → SIMD

HIP programmer 直接建立的是 grid / block / thread hierarchy；wavefront 與 SIMD 則是執行層的重要概念。

Grid = blocks 的集合 ↓ Block / work-group = threads 的集合 ↓ Hardware 將 threads 組成 wavefront ↓ CDNA3/4 course model: 1 wavefront = 64 threads ↓ 16-lane SIMD 分批執行這 64 threads 的 vector instruction

Global 1D index 仍是：

int i = blockIdx.x * blockDim.x + threadIdx.x;

若 blockDim.x=256，一個 block 會包含多個 wavefronts。你不用手動指定「這個 wavefront 跑在哪一個 SIMD」，scheduler 負責 mapping。

課程常用的直覺：64 threads / 16 lanes → 同一 vector instruction 約需要 4 個 lane issue groups 才涵蓋整個 Wave64。
Page 106 / 120Divergence

SIMT 的代價：Branch Divergence 會 mask lanes

同一 wavefront 的 threads 通常共享 instruction flow。如果一部分 threads 走 if、另一部分走 else，硬體會對不活躍 lanes 做 masking，依序完成不同 path，而不是讓一個 wavefront 變成完全獨立的 64 條 instruction streams。

if ((i & 1) == 0) {
    pathA();
} else {
    pathB();
}
Path A 執行：even lanes active / odd lanes masked Path B 執行：odd lanes active / even lanes masked

因此 divergence 可能降低 effective SIMD utilization。這不代表「任何 if 都很慢」；真正問題是同一 wavefront 內大量 threads 走不同路徑。

若題目問 SIMT branch divergence 的典型硬體處理，關鍵詞是 mask inactive lanes。
Page 107 / 120MFMA · GEMM

MFMA：AI matrix engine 的核心 building block

MFMA = Matrix Fused Multiply-Add。概念上一次完成 matrix tile 的 multiply-accumulate：

D = A × B + C

它把大量 scalar FMA 整合成 wave-level matrix operation，讓 dense GEMM、Transformer linear layers、attention matrix multiplications 等 workload 能充分使用 matrix hardware。

Transformer / AI layer ↓ GEMM ↓ rocBLAS / hipBLASLt ↓ MFMA-optimized kernels ↓ Matrix execution hardware
★★★★★：GEMM ↔ rocBLAS/hipBLASLt ↔ MFMA 這三層要能串起來。Associate 不要求你手寫 MFMA ISA。
Page 108 / 120Memory Hierarchy

Memory Hierarchy：越靠近 CU 通常越快、越小

課程用 MI300X/CDNA3 mental model 排出從 on-chip 到 HBM 的階層：

FAST / small VGPR registers ↓ LDS (shared memory) ↓ L1 cache ↓ L2 cache ↓ large cache / fabric-side cache ↓ HBM global memory SLOWER / huge

HBM 的 TB/s 非常高，但相對 registers/LDS 仍有更高 latency。效能最佳化的基本方向是：hot values 留在 registers、block 共享資料放 LDS、讓 cache 幫忙、不要重複從 HBM re-fetch。

考題若問「哪個策略通常改善 memory-bound kernel」，data reuse / coalescing / fewer HBM round trips 都是合理方向。
Page 109 / 120Latency Hiding

GPU 不是消除 memory latency，而是用很多 wavefront 把它藏起來

Wavefront A 若等待 HBM，scheduler 可以改執行已 resident 且 ready 的 Wavefront B，而不讓 SIMD 長時間 idle。這就是 latency hiding 的核心。

WF A: run → memory stall ─────────→ run WF B: ready → run → done WF C: ready ───────────────────────→ ...

因此 GPU 需要大量 threads / wavefronts，不只是為了「平行工作數量多」，也是為了建立足夠的 ready work 來覆蓋 memory latency。

Occupancy 高可能提供更多 resident wavefronts，但 maximum occupancy 不等於 maximum performance：register spill、LDS pressure、cache locality、instruction mix 都會改變結果。

★★★★★：more ready wavefronts → better latency hiding → higher effective throughput；但 occupancy 是手段，不是 KPI 本身。

Page 112 / 120rocBLAS · hipBLASLt

Dense linear algebra：BLAS Levels、GEMM 與 Fusion

BLAS Level 1 是 vector-vector，Level 2 是 matrix-vector，Level 3 是 matrix-matrix。AI 最重要的是 Level 3 的 GEMM：

D = α × A × B + β × C
Level形態例子
1Vector ↔ VectorAXPY、DOT、SCAL、NRM2
2Matrix ↔ VectorGEMV、TRSV
3Matrix ↔ MatrixGEMM、TRSM

rocBLAS 提供標準 dense linear algebra；hipBLASLt 更聚焦可調式 GEMM、layout/type flexibility 與 epilogue/fusion，例如把 bias、activation 跟 GEMM 組合，減少 intermediate HBM traffic 與 kernel launch。

★★★★★：GEMM = BLAS Level 3。看到 dense matrix multiplication / Transformer matmul，優先選 rocBLAS / hipBLASLt。
Page 113 / 120MIOpen Autotune

MIOpen：不只「AMD 的 cuDNN」，還有選 algorithm、調參、cache

MIOpen 提供 convolution、batch normalization、pooling、activations、recurrent primitives、softmax 等 deep-learning building blocks。框架如 PyTorch 可能在 backend 自動使用它。

Fusion 為什麼重要？

Without fusion: conv → HBM → batchnorm → HBM → activation With fusion: conv + normalization/activation → fewer kernels / fewer intermediate HBM accesses

Autotune 三個角色

  • FindDb：記「這個問題該用哪個 solution / implementation」。
  • PerfDb：記「這個 solution 的低階 tuning parameters 應怎麼設」。
  • Kernel cache：重用已編譯 GPU kernel，避免重複 compile。

因此第一次遇到新 shape/type 可能會 search、benchmark、tune、compile；之後相同問題可 reuse。

★★★★★ 口訣：FindDb = which solution；PerfDb = how tuned；Kernel cache = already compiled?
Page 114 / 120rocSOLVER · rocRAND

Solver 與 Random：知道用途，不需要做數學推導

rocSOLVER

Decomposition概念常見用途
LUA=L×U一般 linear systems
CholeskyA=L×LᵀSPD systems
QRA=Q×RLeast squares / regression
SVDA=UΣVᵀPCA、compression、low-rank
EigenAv=λvSpectral analysis、dynamics

rocRAND：PRNG vs QRNG

PRNG 用 deterministic algorithm + seed 產生統計上像隨機的序列，適合 simulation、sampling、stochastic workloads。QRNG 的目標是低 discrepancy、較均勻覆蓋 sample space，常見於 Quasi-Monte Carlo / numerical integration。

Q 是 Quasi，不是 Quantum。兩者都是 software-generated deterministic sequences。
Page 115 / 120rocSPARSE

Sparse matrix：別為 99% 的零浪費 memory 與 compute

若 matrix 幾乎都是 zero，dense representation 會存大量沒用的值。rocSPARSE 支援 sparse matrix/vector operations，只對 non-zero 結構做有效儲存與運算。

Format特性
CSRCompressed Sparse Row；最常見，常用於 SpMV
CSCCompressed Sparse Column；column-oriented
COOCoordinate list；容易 assemble / sort / convert
ELLFixed-width；每 row non-zero 數接近時方便
BSRBlock Sparse Row；適合 dense sub-blocks
HYBHybrid representation，例如 ELL + COO
優先背 CSR = most common、COO = easy assembly、BSR = block sparse。不要把 sparse matrix 題選成 rocBLAS。
Page 116 / 120rocPRIM · Triton · HIP

Parallel primitives 與三層 custom-kernel 選擇

rocPRIM / hipCUB 提供 GPU parallel building blocks：Reduce、Scan（prefix sum）、Sort、Select/filter，避免你把 serial loop 原封不動搬上 GPU。

Reduce: many values → one aggregate Scan: prefix sums / running totals Sort: unordered keys → ordered keys Select: predicate → compacted output

要不要自己寫 kernel？

層級何時用取捨
ROCm libraries標準 operation 已涵蓋最少 code、通常已高度最佳化
TritonCustom/fused kernel，但希望 Python DSL 與 autotune較高 productivity、仍需要 GPU-kernel thinking
HIP C++需要 maximum low-level control最多 code 與 tuning effort
★★★★☆：標準 op → library；custom fusion → Triton；最大低階控制 → HIP。
Page 117 / 120PyTorch · torch.compile

PyTorch on ROCm：熟悉 API，上層不必重寫

HF / vLLM / SGLang / TGI / Lightning ↓ PyTorch torch / autograd / compile ↓ rocBLAS · hipBLASLt · MIOpen · RCCL ↓ HIP / HSA runtime / driver ↓ AMD GPU

PyTorch on ROCm 仍使用 torch.cuda 作為 generic GPU namespace。torch.cuda.is_available() 在 AMD ROCm 環境可以為 True。

torch.compile() 的主線

model = torch.compile(model) ↓ Graph capture ↓ TorchInductor (default backend) ↓ operator fusion + fewer launches + memory planning + optional autotune ↓ Triton kernels and/or ROCm optimized libraries ↓ AMD GPU
★★★★★：torch.compile → TorchInductor → Triton/ROCm libraries。Fusion 的目的之一是減少 kernel launches 與 intermediate HBM reads/writes。
Page 118 / 120RCCL Collectives

RCCL：AMD 的 NCCL counterpart，五種 collective 要看得懂

Collective結果 mental modelAI 情境
All-ReduceReduce 後，每張 GPU 都得到完整 reduced resultData-parallel gradient synchronization
All-Gather每張提供一個 shard，最後每張都有完整集合FSDP / ZeRO-3 gather sharded parameters
Reduce-ScatterReduce 後，每張只拿自己的 reduced shardFSDP / ZeRO gradient sharding
Broadcast一個 source 發給所有 peersInitial parameters/state sync
All-to-All每張對不同 destination 交換不同 chunksMoE token → expert GPU routing

Topology

Node 內可能走 xGMI / Infinity Fabric 或 PCIe；跨 node 常見 InfiniBand、RoCE 或 TCP/IP。RCCL 的價值之一是 topology-aware collective communication。

★★★★★：NCCL → RCCL。All-Reduce = gradients；All-Gather / Reduce-Scatter = sharding；All-to-All = MoE。
Page 119 / 120vLLM Serving

Direct PyTorch inference vs vLLM：flexibility 與 serving throughput 的取捨

Direct PyTorchvLLM
General-purpose model executionSpecialized LLM inference / serving engine
Custom preprocessing / model logic / outputsPagedAttention / KV-cache management
適合 research、custom workflowContinuous batching、high concurrency
直接控制 model pipelineQuantization、OpenAI-compatible API

兩個必懂功能

  • PagedAttention：把 KV cache 以 page/block 方式管理，改善 memory utilization 並降低 fragmentation。
  • Continuous batching：request 完成後，新 request 可以動態補入 active batch，避免等整批全部結束才開始下一批。
★★★★★：custom/flexible inference → PyTorch；高 throughput concurrent LLM serving → vLLM。

20 題情境快速自測

  1. Instinct data-center GPU family primarily maps to which architecture line? CDNA
  2. In the course CDNA3/4 model, a wavefront contains how many threads? 64
  3. Four 16-lane units per CU are examples of what hardware execution engine? SIMD
  4. Same kernel program across many threads, each processing different data? SPMD
  5. Why can divergent branches reduce efficiency? Inactive lanes are masked while different paths execute.
  6. Matrix fused multiply-add used by optimized GEMM kernels? MFMA
  7. Why stage reused data in LDS? Reduce repeated high-latency HBM accesses.
  8. Why keep many wavefronts resident? Hide memory latency.
  9. Dense GEMM library? rocBLAS / hipBLASLt
  10. GEMM belongs to which BLAS level? Level 3
  11. AMD analog/counterpart to cuDNN? MIOpen
  12. MIOpen database that remembers which solution to use? FindDb
  13. MIOpen database for low-level tuning parameters? PerfDb
  14. SVD / QR / LU ROCm library? rocSOLVER
  15. Prefix sum / reduce / sort building blocks? rocPRIM / hipCUB
  16. PyTorch compiler backend behind torch.compile by default? TorchInductor
  17. Custom Python GPU kernel DSL often emitted by TorchInductor? Triton
  18. Gradient synchronization across data-parallel GPUs? RCCL All-Reduce
  19. MoE token routing collective? All-to-All
  20. High-throughput LLM serving with PagedAttention and continuous batching? vLLM
達標線：20 題至少 18 題能直接回答，且能用自己的話解釋原因。若只記答案、不懂資料怎麼從 PyTorch → ROCm library → HIP runtime → GPU hardware，遇到改寫情境題很容易失分。
