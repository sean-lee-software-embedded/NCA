Chapter 6 · CUDA → HIP Porting

Associate 公開考綱明列 porting patterns。重點不是「字串取代」，而是建立可驗證、可維護的 migration workflow。

Page 51 / 100Porting Strategy

移植先求 correctness，再求 performance

CUDA 專案移植到 ROCm 時，先盤點 CUDA runtime APIs、libraries、compiler flags、architecture-specific code、inline PTX、third-party dependencies。最好的流程是建立 baseline tests，讓每一步移植後都能驗證結果。

Inventory CUDA dependencies ↓ HIPIFY / manual conversion ↓ Build on ROCm ↓ Correctness tests ↓ Replace / adapt libraries ↓ Profile ↓ Architecture-aware tuning
若題目問 migration 的「first priority」，通常先確保 code 可 build 且結果正確，再進行 performance optimization。

Page 53 / 100HIPIFY

HIPIFY 做什麼？

HIPIFY 是協助 CUDA source 轉換成 HIP 的工具集合。常見實作包括 hipify-clang 與 hipify-perl。它能自動處理大量 API/token mapping，但輸出仍需要人工 review、build、test。

hipify-clang 使用 Clang parsing/AST，因此能提供更語意化的轉換與診斷；hipify-perl 則較像規則式文字轉換，環境要求較低。

題目問「automatically assists CUDA-to-HIP source conversion」→ HIPIFY。
HIPIFY ≠ 一鍵保證 production-ready。Architecture-specific optimization、unsupported libraries、custom build logic 都可能需要手工處理。
Page 54 / 100Kernel Syntax

為什麼很多 kernel code 幾乎不用改？

HIP 刻意保留大量 CUDA-like kernel syntax，例如 __global__、threadIdx、blockIdx、blockDim。因此許多純 kernel arithmetic code 可以相對平滑地移植。

// CUDA-like source
__global__ void add(float *a,float *b,float *c,int n){
  int i=blockIdx.x*blockDim.x+threadIdx.x;
  if(i<n)c[i]=a[i]+b[i];
}

真正困難通常在 host runtime APIs、libraries、compiler flags、special intrinsics 與 architecture assumptions。

「HIP porting 只需改 kernel syntax」是錯的；完整 migration 要看整個 build/runtime/library stack。

Page 56 / 100Architecture Assumptions

最危險的不是 API，而是偷偷寫死的 NVIDIA 假設

例如程式可能假設某個 warp size、使用 inline PTX、依賴 CUDA-specific intrinsic 或特定 shared memory/bank 行為。這些程式碼即使 HIPIFY 能轉換表面 syntax，也不代表語意與效能相同。

Portability 原則：能從 runtime/query API 取得的 hardware property，不要無必要硬編碼。

另一類問題是 tuning parameters：CUDA 上最佳的 block size、tile size，在 AMD GPU 不一定最佳。因此 correctness port 完成後，需要重新 profile。

「原 CUDA kernel performance 很好，所以 HIP version 一定同樣最佳」是錯的。
Page 57 / 100Build Porting

Makefile / CMake 也要一起移植

Porting 不只改 .cu source。原專案可能用 nvcc flags、CUDA toolkit path、FindCUDAToolkit、link cudart/cublas 等。這些都要轉成 HIP/ROCm toolchain 與 libraries。

Source migration + Build system migration + Dependency migration + CI environment migration + Runtime deployment migration

成熟專案常把 backend abstraction 做好，讓 CUDA/HIP 共用大部分 source，只在 platform layer 分支。Associate 不要求你設計大型 portability architecture，但要知道 build system 也是 migration scope。

Page 58 / 100Correctness Validation

移植後怎麼知道「真的對」？

GPU 浮點計算可能因不同 implementation/order 出現小量數值差異，因此 validation 通常不只做 bitwise equality，而是依 workload 使用 tolerance。

abs(gpu[i] - ref[i]) < atol + rtol * abs(ref[i])

對 vector integer operation 可 exact compare；對 FP16/BF16/deep learning workload 則需合理 tolerance 與 domain-specific metric。

Correctness validation 應在 performance tuning 之前。否則你可能把「跑得很快但答案錯」當成優化成果。
Lab：為 vectorAdd 寫 CPU reference，逐元素檢查 HIP output。
Page 59 / 100Porting Failures

常見移植失敗分類

  1. Unsupported API：HIPIFY 報未支援或無直接 mapping。
  2. Library gap：原 CUDA library 功能需找 ROCm alternative。
  3. Build flags：nvcc-specific options 無法直接使用。
  4. Architecture code：inline PTX / warp assumptions。
  5. Correctness：race、floating-point behavior、initialization。
  6. Performance：memory layout、tile/block configuration 不適合 AMD target。
排查順序：先能 build → 能 run → 結果正確 → profiler → tune。
Page 60 / 100Porting Lab

Lab：自己做一次 CUDA-style → HIP migration

準備一個小型 CUDA vector add sample（不需要 NVIDIA GPU 執行也能閱讀 source），完成：

  1. 列出所有 cuda* APIs。
  2. 手動寫出 HIP mapping。
  3. 用 HIPIFY 結果與手動 mapping 比對。
  4. 用 hipcc build。
  5. 跑 CPU reference 驗證。
  6. 用 profiler 看 kernel + copy 時間。
本章完成標準：看到 CUDA code，不只會把 cudaMalloc 改 hipMalloc，還知道 libraries、build system、architecture assumptions 與 validation 都屬於 porting 工作。
