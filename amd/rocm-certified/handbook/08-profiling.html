Chapter 8 · Profiling & Debugging

Debugging 回答「為什麼錯」，profiling 回答「時間花在哪裡、資源怎麼用」。兩者工具與目的不同。

Page 71 / 100Tool Map

先建立 ROCm 工具地圖

工具主要用途
rocminfoRuntime/agent/device capability 資訊
AMD SMI / amd-smiGPU inventory、utilization、memory、power、temperature 等管理/監控

遇到工具選擇題先看問題是「device inventory」、「程式 crash」、「timeline」、「kernel performance」中的哪一種。
Page 72 / 100rocminfo

rocminfo：先確認 runtime 看得到什麼

rocminfo 會列出 HSA agents、GPU architecture/capabilities 等資訊。它不是單純 temperature monitor，而是 runtime/device capability discovery 工具。

rocminfo
rocminfo | grep -i -E 'name|gfx|wavefront|workgroup'

當 HIP 程式完全找不到 GPU，rocminfo 是很好的第一層檢查。如果 rocminfo 正常，而某 framework 不正常，問題更可能在 container/framework/application layer。

問「What command displays ROCm agent/device information?」→ rocminfo。
Page 73 / 100AMD SMI

AMD SMI：觀察 GPU 是否真的在工作

AMD SMI 用於查詢與管理 AMD GPU 的狀態。常見資訊包括 device inventory、GPU/memory utilization、temperature、power、memory usage 等；可把它視為 AMD GPU 運維視角的重要工具。

amd-smi
amd-smi monitor   # exact subcommands depend on installed version

不同 AMD SMI 版本的 CLI 子命令可能演進，因此實作時先看 amd-smi --help。

不要把 amd-smi 當 profiler。它能看到總體 utilization，但不能取代 kernel timeline/counter profiler。
Lab：一個 terminal 跑 matrix workload，另一個看 amd-smi utilization/memory 變化。
Page 74 / 100Debugging

GPU bug 先分四類

  1. Build-time：compile/link 失敗。
  2. Launch/runtime：invalid configuration、device image、allocation failure。
  3. Memory correctness：out-of-bounds、use-after-free、race。
  4. Numerical correctness：結果跑完但與 reference 不一致。

不同類別需要不同工具。Build-time 看 compiler/linker；runtime 先檢 HIP errors；memory/source-level 再用 debugger 或 sanitizer-like tooling；numerical 則用 CPU reference、small input、deterministic test。

Debug 的第一步通常是縮小問題範圍，而不是直接開最重的 profiler。
Page 75 / 100ROCgdb

ROCgdb：source-level debugging 的概念

ROCgdb 是基於 GDB 的 ROCm debugger，可用熟悉的 breakpoint、backtrace、source inspection 等概念除錯 host/device code。對已熟 GDB 的人，mental model 很容易轉移。

rocgdb ./app
(gdb) break main
(gdb) run
(gdb) bt

GPU kernel debugging 會比 CPU 更複雜，因為同時有大量 threads。實際命令依 ROCgdb version 與 debug info 而定；Associate 重點是知道它負責 source-level debugging。

Release -O3 binary 可能很難 debug。需要保留 debug symbols、適當降低 optimization 才容易對應 source。
Page 76 / 100rocprofv3

rocprofv3：先看 timeline，再決定深入哪裡

目前 ROCm profiling 工具鏈以 ROCprofiler-SDK / rocprofv3 為重要方向。舊教材可能仍出現 rocprof、rocprofv2、ROCTracer 等名稱；閱讀時要知道工具已演進。

Timeline 能回答：哪個 kernel 最久？memcpy 是否佔很多時間？kernels 之間是否有空洞？不同 streams 是否 overlap？

CPU API calls ─────┐ H2D copy ███ │ Kernel A ███████ Kernel B ██ D2H copy ███
如果問題是「找出 application 中最耗時 kernel」，先 profiler/timeline，而不是 ROCgdb。
Page 77 / 100Counters

Hardware counters：從「慢」進一步問「為什麼慢」

Timeline 只告訴你 kernel A 花 10 ms；hardware counters 才能進一步揭示 memory bandwidth、cache behavior、instruction activity、occupancy/resource 等特徵。

分析順序應是：先找 hotspot → 再針對 hotspot 收 counters。不要一開始對所有 kernels 收大量 counters，資料會太多且 profiling overhead 可能上升。

Profiler 的角色是 measurement。最佳化前應先建立 baseline，改完後再量一次，比較是否真的變快。
Lab：對故意使用 strided memory access 的 kernel 與 coalesced version 做 timing，比較差異。
Page 78 / 100Async Errors

為什麼錯誤常在 synchronize 才出現？

GPU kernel launch 通常是 asynchronous。Host 把工作 enqueue 後可能立刻繼續，因此 kernel 內 illegal access 不一定在 launch call 當下就回報。

hipLaunchKernelGGL(badKernel,...);
HIP_CHECK(hipGetLastError());          // launch-level error
HIP_CHECK(hipDeviceSynchronize());     // execution-time error may surface here

這也是 debug 時刻意加 synchronize 的價值：雖然 performance 變差，但能把錯誤定位到較靠近真正發生的位置。

Debug build 可以多同步，production build 不要無腦保留所有 sync。
Page 79 / 100Performance Triage

看到「GPU 很慢」時的 triage tree

GPU slow ├─ GPU hardly busy? → launch gaps / CPU bottleneck / transfers / small workload ├─ Memory bandwidth high, compute low? → memory-bound ├─ Compute high? → compute-bound / algorithm / datatype ├─ Low occupancy? → registers / LDS / block size ├─ Many tiny kernels? → launch overhead / fusion └─ Large H2D/D2H? → reduce transfers / pipeline

這棵樹不代表所有 profiler metric 的完整定義，但足以讓 Associate 情境題有系統地推理。

不要看到「slow」就回答「increase occupancy」。先確認瓶頸是哪一類。
Page 80 / 100Debug Lab

Lab：刻意做壞一支 HIP 程式

  1. 把 buffer allocation 改小，製造 out-of-bounds。
  2. 每個 runtime call 加 HIP_CHECK。
  3. 在 launch 後加 hipGetLastError + synchronize。
  4. 用 ROCgdb / available debug tool 取得 crash context。
  5. 修好 correctness。
  6. 用 profiler 建立 timeline baseline。
