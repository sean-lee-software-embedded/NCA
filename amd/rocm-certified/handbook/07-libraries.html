Page 61 / 100Library Strategy

先用 optimized library，還是自己寫 HIP kernel？

如果問題屬於成熟 domain，例如 GEMM、FFT、convolution、collective communication，通常優先使用 ROCm optimized library。這些 libraries 已針對 architecture、datatype、memory access 做大量 tuning。

Known operation? ├─ GEMM → rocBLAS / hipBLAS ├─ DNN op → MIOpen ├─ FFT → rocFFT / hipFFT ├─ Random → rocRAND / hipRAND ├─ Sparse → rocSPARSE / hipSPARSE └─ Collective → RCCL Unknown/custom algorithm → HIP kernel
題目若提供標準矩陣乘法需求，通常不需要手刻 matrix multiply kernel。
Page 62 / 100rocBLAS

rocBLAS：Dense linear algebra 的核心

rocBLAS 實作 BLAS standard 的高效 GPU operations，例如 vector operations 與 GEMM。AI/HPC 中大量矩陣乘法都可落到 BLAS primitives。

概念上，使用 rocBLAS 時 programmer 提供 matrix pointers、dimensions、leading dimensions、datatype 等，而 library 選擇 optimized kernel。這比自己管理 thread/block/LDS 的抽象層更高。

cuBLAS → rocBLAS 是最重要 mapping 之一；如果程式重度使用 GEMM，porting 時先研究 rocBLAS/hipBLAS。
BLAS layout 容易出錯：row-major/column-major、leading dimension、transpose flags 會影響 correctness。
Page 63 / 100MIOpen

MIOpen：Deep Learning primitives

MIOpen 是 ROCm 生態中的 deep learning library，提供 convolution、normalization、activation 等常用 primitives，以及演算法選擇與最佳化能力。概念上最常與 NVIDIA cuDNN 對照。

Framework user 未必直接呼叫 MIOpen API；PyTorch 等 framework 可能在 backend 中透過 MIOpen 使用 optimized implementation。

Healthcare、LLM、vision 等「application domain」不是 MIOpen 的定義；MIOpen 的角色是 deep learning primitives。
口訣：cuDNN 的 DNN → AMD MIOpen。
Page 64 / 100RCCL

RCCL：Multi-GPU collective communication

RCCL 提供 all-reduce、all-gather、broadcast、reduce-scatter 等 collective operations，常用於 distributed training。它在 ROCm 生態中的概念位置對應 NVIDIA NCCL。

GPU0 gradients ─┐ GPU1 gradients ─┼─ AllReduce → each GPU gets reduced result GPU2 gradients ─┼ GPU3 gradients ─┘

Associate 主要需要知道 collective 的用途，不必深入 ring/tree algorithm tuning。

題目說「四張 GPU 訓練，需要交換/聚合 gradients」→ RCCL；不是 rocBLAS。

Page 66 / 100hip Libraries

hipBLAS / hipFFT / hipRAND：portable interface 的概念

ROCm 生態同時有 roc* 與 hip* library names。簡化理解：roc* 多為 AMD ROCm native optimized library；hip* API 常提供較 portable 的介面，讓 source 更容易跨 backend。

例如 hipBLAS 可作為 BLAS portability layer，底層在 AMD 平台使用對應 ROCm implementation。考試若問「native ROCm BLAS library」偏 rocBLAS；若情境強調 portable API，可能偏 hipBLAS。

不要硬背一句「hipBLAS=rocBLAS」。它們層次與 API 目的不同，雖然功能 domain 重疊。
Page 67 / 100PyTorch

PyTorch on ROCm 為什麼還是 torch.cuda？

PyTorch 在 ROCm 上仍使用 torch.cuda namespace 作為 generic GPU interface。這是非常容易誤判的考點。

import torch
print(torch.cuda.is_available())
print(torch.cuda.get_device_name(0))
print(torch.version.hip)

在正常 ROCm PyTorch 環境，torch.cuda.is_available() 可以回 True，device name 則顯示 AMD GPU。

不存在一套你必須改成 torch.rocm.* 的平行 API。看到 AMD GPU 不要直覺把所有 cuda namespace 改名。
Lab：在 ROCm container 裡執行以上三行，確認 framework、GPU 與 HIP version。
Page 68 / 100Framework Stack

Framework failure 要在哪一層排查？

當 PyTorch 看不到 GPU，不要立刻怪 model code。依序確認：host GPU/device access → ROCm runtime → container/device mapping → framework build → application。

amd-smi / rocminfo works? ↓ yes container sees device? ↓ yes torch.version.hip present? ↓ yes torch.cuda.is_available()? ↓ yes then debug model/application

這種 layered troubleshooting 與 build domain 的思路一致：先找到故障所在層級，再深入。

如果 rocminfo 本身就看不到 GPU，重裝 Python package 通常不是最佳第一步。

Page 70 / 100Chapter Drill

Libraries 一頁總結

Associate 的「libraries awareness」重點可壓成：

Linear algebra → rocBLAS DNN primitives → MIOpen Collectives → RCCL FFT → rocFFT Random → rocRAND Sparse → rocSPARSE Portable family → hipBLAS / hipFFT / hipRAND / hipSPARSE Custom operation → HIP kernel
本章完成標準：任何一個典型 workload 描述，你能在 5 秒內選出 library family，並知道其 NVIDIA 對應（若有）。
進階 Lab：跑一個 PyTorch matrix multiply，用 profiler 觀察底層 GPU activity；目標不是解析所有 internal kernel 名稱，而是建立「framework 最終仍落到 GPU kernels/libraries」的感覺。
