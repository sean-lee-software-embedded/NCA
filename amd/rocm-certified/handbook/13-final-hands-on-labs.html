Hands On Lab 1Module 3

Lab 1：ROCm Libraries + PyTorch，先學會不要重造輪子

這個 Lab 的 mental model 是：常見數學與 AI primitive，優先交給 AMD 已最佳化的 library；framework 再把這些 library 串成完整 workload。

Exercise A · rocBLAS SGEMM

C = α × op(A) × op(B) + β × C
FLOPs ≈ 2 × M × N × K
GFLOPS = FLOPs / seconds / 1e9

考點：GEMM 是 general matrix multiplication；GFLOP 是工作量，GFLOPS / TFLOPS 才是 throughput。比較 theoretical peak 時要對齊 datatype，例如 FP32 workload 不要拿 FP8 peak 當 denominator。

Exercise B · PyTorch Conv2D → MIOpen

torch.nn.functional.conv2d ↓ PyTorch ROCm backend ↓ MIOpen solver / kernel ↓ HIP runtime ↓ AMD GPU

第一次執行可能含 runtime 初始化、solver selection、cache lookup 或 kernel preparation，所以 first-call time 常比 steady-state 慢。

考點：MIOpen 對應 NVIDIA 世界最接近 cuDNN；它處理 convolution 與其他 deep-learning primitives。

Exercise C · rocFFT round-trip

signal = torch.randn(N, device='cuda')
spectrum = torch.fft.fft(signal)
recovered = torch.fft.ifft(spectrum).real
error = (signal - recovered).abs().max()

正確性是 ifft(fft(x)) ≈ x，不是 bit-identical。浮點 round-off 會累積，因此要用合理 tolerance 驗證。

Exercise D · PyTorch training loop

optimizer.zero_grad()
outputs = model(inputs)
loss = criterion(outputs, labels)
loss.backward()
optimizer.step()

這五步要能不看答案解釋。model.train() 只是切 training mode；真正 parameter update 是 optimizer.step()。

ROCm 易錯點：PyTorch on ROCm 仍使用 torch.cuda namespace，例如 torch.cuda.is_available()。

Exercise E · Troubleshooting ladder

amd-smi ↓ hardware / driver visibility rocminfo ↓ HSA / ROCm visibility python: torch.version.hip ↓ correct ROCm PyTorch build? torch.cuda.is_available() ↓ framework sees GPU? torch.mm(...) ↓ real compute succeeds?

Debug 原則：先找「最底下哪一層開始壞」，不要一看到 PyTorch error 就直接重裝整套環境。

Hands On Lab 2Module 4

Lab 2：HIP Programming + CUDA Porting

這個 Lab 從「library user」切換成「GPU kernel programmer」。最重要的是 thread indexing、bounds check、memory lifecycle、asynchronous execution 與 parallel correctness。

Exercise A · Vector Add from scratch

__global__ void vec_add(const float* A,
                        const float* B,
                        float* C, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) C[i] = A[i] + B[i];
}

int threads = 256;
int blocks = (N + threads - 1) / threads;
vec_add<<>>(d_A, d_B, d_C, N);
Expression意思
threadIdx.xthread 在 block 內的 index
blockIdx.xblock 在 grid 內的 index
blockDim.x每個 block 的 threads 數
blockIdx.x*blockDim.x+threadIdx.xglobal thread index

Exercise B · asynchronous error handling

kernel<<>>(...);
HIP_CHECK(hipGetLastError());
HIP_CHECK(hipDeviceSynchronize());

hipGetLastError() 常用來抓 immediate launch/config error；hipDeviceSynchronize() 讓 asynchronous execution error 有機會回到 host。

Debug 時多同步可以讓錯誤靠近真正出錯的位置；performance code 則不要習慣性在每個 kernel 後都同步，否則會破壞 overlap / concurrency。

Exercise C · CUDA → HIP / HIPIFY

CUDAHIP
cudaMallochipMalloc

CUDA source ↓ hipify-perl / hipify-clang ↓ HIP source ↓ manual semantic review ↓ build → correctness test → profile → tune

考點：HIPIFY 做 mechanical conversion，不會自動理解每個自訂 macro、CUDA-only library 或硬體假設。Source portability ≠ performance portability。

Exercise D · Histogram：shared memory + atomic + grid-stride

__shared__ int local_bins[256];

for (int i = threadIdx.x; i < 256; i += blockDim.x)
    local_bins[i] = 0;
__syncthreads();

for (int i = global_id; i < N; i += blockDim.x * gridDim.x)
    atomicAdd(&local_bins[data[i]], 1);
__syncthreads();

for (int i = threadIdx.x; i < 256; i += blockDim.x)
    atomicAdd(&bins[i], local_bins[i]);

shared/LDS privatization 降低 global contention；atomic 解決 race/correctness；grid-stride loop 讓 thread 可以處理多個 index。三個概念不要混成同一件事。

Exercise E · Parallel Reduction

__shared__ float sdata[256];
sdata[threadIdx.x] = (gid < N) ? input[gid] : 0.0f;
__syncthreads();

for (unsigned s = blockDim.x/2; s > 0; s >>= 1) {
    if (threadIdx.x < s)
        sdata[threadIdx.x] += sdata[threadIdx.x + s];
    __syncthreads();
}

Reduction 的 mental model：many values → per-block partial sum → final sum。shared data 被同一 block 的多 threads 讀寫時，barrier placement 直接影響 correctness。

Hands On Lab 3Module 5

Lab 3：Performance Optimization & Profiling

這個 Lab 最重要的不是記某個 benchmark 數字，而是建立一個固定流程：

Measure baseline ↓ Profile ↓ Classify bottleneck ↓ Apply targeted optimization ↓ Validate correctness ↓ Re-measure

Exercise A · Roofline：先問 memory-bound 還是 compute-bound

Arithmetic Intensity = FLOPs / bytes transferred

低 Arithmetic Intensity 通常偏 memory-bound；高 AI 才比較可能逼近 compute ceiling。對 memory-bound kernel，增加 occupancy 的主要價值是幫忙 hide memory latency，但不能把速度推過 memory-bandwidth roof。

Exercise B · Memory hierarchy

大致順序特性
Registers最快、最小、per-thread
LDS / shared memoryon-chip、per-workgroup、可重用資料
Cache硬體管理、介於 on-chip 與 HBM
HBM / global memory容量大但 latency 高，效能高度依賴 access pattern
Host memory通常需要經 PCIe / interconnect，最不適合頻繁來回搬

Exercise C · Naive Transpose → LDS Tiled Transpose

Naive: HBM contiguous read → HBM strided/uncoalesced write Tiled: HBM coalesced read → LDS tile → synchronize → read transposed from LDS → HBM coalesced write
#define TILE 16
__shared__ float tile[TILE][TILE + 1];

// load coalesced
tile[ty][tx] = input[srcY * width + srcX];
__syncthreads();

// swap axes and store coalesced
output[dstY * height + dstX] = tile[tx][ty];

TILE+1 的 padding 主要用來改變 LDS row stride、降低 bank-conflict pattern。Coalescing 是 global/HBM transaction 問題；bank conflict 是 LDS 內部問題。

所有 threads 都必須一致抵達 block-wide barrier；不要把必要的 __syncthreads() 放進只有部分 edge threads 會進入的條件式。

Exercise D · Workgroup / block-size sweep

64 → 128 → 256 → 512 → 1024 threads/block
measure each configuration

Block size 影響 resident waves、resource pressure、latency hiding 與 scheduling；不是越大越快，也不是 occupancy 越高越快。最可靠方法就是 sweep + profile + verify。

Exercise E · FP32 / FP16 / BF16

FormatExponentFraction直覺
FP32823最高 precision baseline
FP16510fraction 較多，precision 通常優於 BF16
BF1687與 FP32 同 exponent width，dynamic range 較大

Reduced precision 的 decision 不能只看 throughput。正確流程是：同一組 FP32 source data → cast → 執行低精度版本 → 比較 speed + numerical error。
