Chapter 2 · GPU 架構與執行模型

HIP 程式的每一個 index、block size、memory choice，背後都跟 GPU 如何執行大量平行工作有關。

Page 11 / 100CPU vs GPU

CPU 與 GPU：不是誰比較快，而是工作型態不同

CPU 擅長少量複雜 control flow、低延遲與大型 cache；GPU 則用大量運算資源同時處理相似工作。向量加法、矩陣運算、影像處理、深度學習等 data-parallel workload 特別適合 GPU。

CPU: few powerful cores → latency oriented GPU: many parallel execution lanes → throughput oriented

把迴圈搬到 GPU 並不保證變快。若資料太小、host-device copy 太頻繁、kernel launch overhead 比計算本身還大，CPU 反而可能更有效率。

情境題若問「哪種 workload 最適合 GPU」，優先選大量獨立、相似計算，而不是大量 serial dependency 的控制流程。
Page 12 / 100Compute Unit

Compute Unit（CU）是 AMD GPU 的重要運算單位

AMD GPU 由多個 Compute Units 組成。對 HIP programmer 來說，通常不直接指定「這個 block 跑在 CU 3」，而是提交 grid，硬體與 runtime 會把 work-groups 排程到可用 CU。

每個 CU 具有執行 SIMD 工作的資源、register file、Local Data Share（LDS）等。block 的 register 與 LDS 使用量會影響同一個 CU 同時能 resident 多少 work-groups，進而影響 occupancy。

不要把 CU 等同 CPU core。兩者都可以粗略視為運算資源，但 execution model 完全不同。
想像題：一個 kernel 每個 block 使用大量 LDS，為什麼可能降低 occupancy？因為單一 CU 可供多個 resident blocks 共用的 LDS 是有限資源。
Page 13 / 100Thread

Thread / Work-item：最小的程式實例

在 HIP kernel 中，每個 thread 執行同一份 kernel code，但用自己的 thread index 處理不同資料。例如：

__global__ void scale(float *x, float a) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    x[i] *= a;
}

這段 code 的核心思想不是「kernel 有一個 i」，而是成千上萬個 threads 各自算出不同 i。

threadIdx.x 是 thread 在 block 內的 index；它不是整個 grid 的 global index。
練習：blockDim.x=256、blockIdx.x=3、threadIdx.x=7，global index = 3×256+7 = 775。
Page 14 / 100Block

Block / Work-group：可以合作與同步的 thread 群組

同一個 block 內的 threads 可透過 shared memory（AMD 硬體對應 LDS）共享資料，並使用 block-level synchronization。不同 blocks 則不能假設同時執行，也不能靠一般 block barrier 互相同步。

__shared__ float tile[256];
tile[threadIdx.x] = input[i];
__syncthreads();
// all threads in this block now see completed tile loads

這種模式常用於 tiling：先把 global memory 的資料載入高速 on-chip LDS，再重複使用。

常見錯誤：__syncthreads() 只同步 block 內 threads，不是整顆 GPU 的 global barrier。
Page 15 / 100Grid

Grid：一次 kernel launch 的所有 blocks

Grid 是一個 kernel launch 所建立的全部 blocks。你通常用 problem size 和 threads-per-block 算 grid size：

int threads = 256;
int blocks = (N + threads - 1) / threads;
hipLaunchKernelGGL(kernel, dim3(blocks), dim3(threads), 0, 0, ...);

(N + threads - 1) / threads 是常見 ceiling division，確保即使 N 不是 256 的倍數，也會啟動足夠 threads。

既然最後一個 block 可能有多餘 threads，kernel 內通常需要 if (i < N) 邊界檢查。
Page 16 / 100Wavefront

Warp / Wavefront：lockstep 執行的 thread 群

HIP 文件會使用 warp 這個 portable programming term，而 AMD ISA 常稱 wavefront。這是實際執行與排程的重要群組：一組 threads 以 lockstep 方式執行同一條指令。

若同一個 wavefront 裡發生分支，一部分 threads 走 if、另一部分走 else，硬體可能需要分開執行兩條路徑，這就是 branch divergence 帶來的效率損失。

if (threadIdx.x % 2 == 0) {
    pathA();
} else {
    pathB();
}
Associate 不一定要求背每代 GPU 的 wave size，但要理解「同一 wave 中 divergence 可能降低效率」。
Page 17 / 1003D Indexing

x/y/z 維度：讓資料形狀對應 thread hierarchy

HIP 的 thread、block、grid 都可用 x、y、z 三個維度。1D 適合 vector；2D 適合 image/matrix；3D 適合 volume 或 spatial simulation。

int x = blockIdx.x * blockDim.x + threadIdx.x;
int y = blockIdx.y * blockDim.y + threadIdx.y;
if (x < width && y < height) {
    output[y * width + x] = ...;
}

2D launch 例：

dim3 block(16,16);
dim3 grid((width+15)/16, (height+15)/16);
hipLaunchKernelGGL(kernel, grid, block, 0, 0, ...);
練習：1920×1080 image 用 16×16 block，grid.x=120，grid.y=68；最後一列仍需 bounds check。
Page 18 / 100Scheduling

不要假設 blocks 的執行順序

Grid 中不同 blocks 由硬體動態排程到可用 CUs；順序可能不是 block 0、1、2 依序完成。程式正確性不能依賴某個 block 一定先跑。

如果 kernel A 的結果要給 kernel B 使用，常見做法是利用 stream ordering 或 host-side synchronization，讓 kernel B 在 A 完成後再執行，而不是在 A 的不同 blocks 之間硬做全域同步。

題目若暗示「block 1 可以假設 block 0 已經完成」，通常是危險設計。
跨 block 通訊：可以透過 global memory、atomics 等機制，但需要非常小心 memory ordering；Associate 先掌握不要依賴 block execution order 即可。
Page 19 / 100Occupancy

Occupancy 是資源利用指標，不是最終目標

Occupancy 可理解為 CU 上能 resident 的 active warps/wavefronts 相對於硬體最大能力的程度。高 occupancy 有助於當某個 wave 等 memory 時，scheduler 切去執行其他 ready waves，以隱藏 latency。

但 occupancy 並非越高越好。某些 kernel 即使 occupancy 中等，也可能因為 cache locality、register reuse、instruction efficiency 很好而更快。

考試陷阱：「Maximum occupancy always means maximum performance」是錯的。最終要量測 application performance。

影響 occupancy 的常見資源：registers per thread、LDS per block、block size、hardware wave slots。

Page 20 / 100Chapter Drill

執行模型 10 分鐘總複習

Grid ├─ Block 0 │ ├─ Wavefront(s) │ │ └─ Threads │ └─ Shared LDS ├─ Block 1 └─ ... Global index (1D) = blockIdx.x * blockDim.x + threadIdx.x
  1. Thread：kernel 的單一平行實例。
  2. Block：可共享 LDS、可 block-level sync 的 threads 群。
  3. Grid：一次 launch 的全部 blocks。
  4. Wavefront：lockstep 執行群組，divergence 可能有成本。
  5. CU：實際承載 work-groups 的硬體運算單位。
  6. Occupancy：可用來理解 latency hiding，但不是唯一 performance metric。
