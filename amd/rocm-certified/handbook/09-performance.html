Associate 不要求極致 microarchitecture tuning，但要能辨識常見 bottleneck，並知道最佳化前後都要量測。

Page 81 / 100Baseline

所有最佳化的第一步：建立 baseline

沒有 baseline 的「感覺變快」沒有意義。記錄 input size、GPU、ROCm version、compiler flags、warm-up 策略與 measurement 方法，才能公平比較。

# concept only
run warmup several times
measure repeated runs
report median/average with same input

GPU 第一次執行可能包含初始化、cache、module loading 等一次性成本。對 microbenchmark 要把這些與 steady-state kernel time 分開。

如果題目問「如何確認 optimization 有效」，答案應包含 profile/measure before and after，而不是只看 source code。
Page 82 / 100Memory Bound

Memory-bound kernel：算力不是主要限制

Vector add 每個元素只做少量 arithmetic，卻需要讀 a、讀 b、寫 c，因此常偏 memory bandwidth bound。加更多 arithmetic units 不一定提升速度；改善 memory access、coalescing、reuse 才更重要。

Arithmetic intensity = operations / bytes moved Low intensity → often memory-bound High intensity → more likely compute-bound

Associate 不必做完整 roofline analysis，但要理解「memory bandwidth 已滿、compute utilization 不高」不代表 GPU 壞掉，可能是 workload 特性。

思考：vector add 與大型 GEMM，哪個通常 arithmetic intensity 高？GEMM。
Page 83 / 100Compute Bound

Compute-bound：考慮 datatype、matrix acceleration 與算法

若 profiler 顯示 compute resources 高度忙碌、memory bandwidth 不是限制，下一步可能是減少 operations、使用更適合的 datatype、採用 optimized library 或演算法。

AI workload 常使用 FP16/BF16 等 mixed precision，降低 memory footprint 並利用 matrix acceleration；但需確認 numerical correctness / convergence。

Mixed precision 不是免費午餐。它可能改變數值範圍與 precision，必須用 workload metric 驗證。
標準 GEMM 若有 rocBLAS optimized implementation，通常比自己寫 naïve kernel 更合適。
Page 84 / 100Occupancy Tuning

Block size、register、LDS：occupancy 的三角關係

Block size 過小可能不足以提供平行工作；過大則可能因 registers/LDS 資源壓力限制 resident blocks。常見 block size 如 128/256 是起點，不是永遠的答案。

Higher block size ↕ more threads per block ↕ register & LDS resource demand ↕ resident blocks / occupancy

正確流程是用 profiler/occupancy calculator-like data 觀察，再 benchmark 幾個合理 configuration。

「256 threads always optimal」是錯的。最佳 block size 依 kernel 和 target architecture 而異。
Page 85 / 100Kernel Launch

很多 tiny kernels：launch overhead 可能比計算還大

若 application 啟動大量極短 kernel，CPU launch overhead、synchronization、framework dispatch 可能形成明顯空洞。可能的改善包括 kernel fusion、批次處理、更大的 work unit，或減少不必要 sync。

Bad timeline: K K K K K K K K (each kernel tiny, gaps dominate) Better concept: ████ Fused / batched work ████
Fusion 也有 trade-off：過大的 fused kernel 可能提高 register pressure 或降低 reuse，因此仍需量測。
Page 86 / 100Transfer Optimization

把資料搬一次，比把同一份資料搬十次重要

最有效的 transfer optimization 常不是換一個更快的 memcpy API，而是改 application flow：把中間結果留在 device、連續執行多個 kernels，只在必要時回 host。

若無法避免 transfer，再考慮 pinned memory、async copy、chunking、streams 與 overlap。

題目若說「每個 layer 都把 tensor copy 回 CPU 再送回 GPU」，第一優先是消除不必要 round trips。
Lab：比較 100 次小 H2D copy 與一次合併大 copy 的時間。
Page 87 / 100Divergence

Branch divergence：同一 wave 走不同路徑的成本

若同一個 wave 的 threads 對條件判斷產生不同結果，硬體可能需要把不同 path 依序執行並 mask 不參與的 lanes。這會降低 SIMD/SIMT efficiency。

if (data[i] > threshold) fastPath();
else slowPath();

不是所有 if 都要消滅；如果同一 wave 中大多 threads 走同一條路，成本可能不高。最佳化前仍應 profile。

不要為了消除分支寫出更多昂貴運算。最終看 performance，不是看 source 是否「漂亮」。

Page 89 / 100Lab 2

Hands-on Lab：Correctness → Profiling → Optimization

  1. 寫 vectorAdd。
  2. 用 CPU reference 驗證。
  3. 量 baseline kernel/copy time。
  4. 改成故意 strided access，觀察變慢。
  5. 恢復 coalesced access。
  6. 改成 async copy + stream（有 pinned memory 時）。
  7. 比較 end-to-end time。
這個 lab 把 Associate 的 HIP fundamentals + profiling/debugging + performance mental model 串在一起。

記住：只看 kernel time 可能忽略 transfer；只看 end-to-end 又可能看不出 kernel hotspot。兩種 measurement 都有價值。
