Chapter 4 · Memory 與 Concurrency

GPU 效能問題很大一部分不是算術慢，而是資料「放哪裡、怎麼搬、能不能重疊執行」。

Page 31 / 100Memory Hierarchy

GPU memory hierarchy：速度、容量、scope 都不同

HIP programming model 常見的 memory 層級可從 thread-local registers、block-shared LDS 到 device-wide global memory/HBM 來理解。越靠近 execution units 通常容量更小、延遲更低。

MemoryScope特性
RegistersPer-thread最快、容量有限；過多會影響 occupancy 或 spill。
LDS / shared memoryPer-blockOn-chip、可讓 block threads 合作與重用資料。
Global memory / HBMDevice-wide容量大、延遲較高；access pattern 很重要。
題目若問「同一 block threads 要共享重複使用的小型 tile」，優先想到 shared memory / LDS，而不是反覆讀 global memory。
Page 32 / 100Registers

Registers 很快，但不是越多越好

每個 thread 的暫存變數通常盡量放 registers。Register access 非常快，但 CU 的 register file 是有限資源；每個 thread 使用過多 registers，可能讓同一 CU 能 resident 的 wavefront 數下降。

若 register 壓力太高，compiler 甚至可能 spill 到較慢的 memory，造成顯著 performance penalty。

常見誤解：「把所有資料都放 register 一定最快」不成立，因為 resource pressure 會改變 occupancy，而且大量資料根本放不下。
效能思考：當 profiler 顯示 occupancy 低時，不只看 block size，也要檢查 register usage 與 LDS usage。
Page 33 / 100LDS

LDS / shared memory：手動管理的高速共享區

典型 tiling 流程是：threads 從 global memory 合作載入 tile → __syncthreads() → 在 LDS 重複計算 → 再同步 → 寫回 global memory。這可以減少昂貴的 global transactions。

__shared__ float tile[256];
int t = threadIdx.x;
tile[t] = input[base + t];
__syncthreads();
float v = tile[(t+1) & 255];

但 LDS 也有 bank organization；不良 access pattern 可能造成 bank conflicts，讓原本應平行的 access 被序列化。

Global memory 著重 coalescing；shared memory/LDS 常見議題是 bank conflict。兩者不要混為一談。
Page 34 / 100Global Memory

Coalesced access：讓相鄰 threads 存取相鄰位址

當同一 wave/warp 中的 consecutive threads 存取 consecutive、對齊的 memory locations，memory controller 較能把多個要求合併成較少 transactions，提升 effective bandwidth。

Good: T0 → A[0] T1 → A[1] T2 → A[2] T3 → A[3] Bad / strided: T0 → A[0] T1 → A[64] T2 → A[128] T3 → A[192]
不要只看演算法複雜度。兩個 O(N) kernels 可能因 memory access pattern 不同而差很多。
練習：2D matrix 若 row-major，通常讓相鄰 x threads 存取同一 row 的連續元素更容易 coalesce。
Page 35 / 100Host Device Transfer

Host↔Device transfer 是常見瓶頸

若每次只做很少 GPU 計算，卻頻繁把資料 CPU→GPU→CPU，transfer overhead 可能把 acceleration 優勢完全吃掉。最佳化通常先問：資料能否在 GPU 上多停留一段時間？多個 operations 能否串在 device memory 上完成？

Poor: H→D → kernel → D→H → H→D → kernel → D→H Better: H→D → kernel1 → kernel2 → kernel3 → D→H
情境題：GPU utilization 低且大量時間花在 memcpy，最佳第一步通常是減少/合併 transfers，而不是盲目加大 block size。
Page 36 / 100Pinned Memory

Pinned host memory：為更有效率的 DMA 做準備

一般 pageable host memory 可能需要額外 staging；pinned（page-locked）memory 可讓 device DMA 更直接地傳輸，常搭配 asynchronous copy 使用。

float *h = nullptr;
hipHostMalloc(&h, bytes);
// use h
hipHostFree(h);

Pinned memory 是有限且對系統有成本的資源，不應把所有 host memory 都鎖住。

考試思維：Pinned memory 的優勢是 transfer / async pipeline，不是 GPU kernel 執行時把它當成 register。
Page 37 / 100Unified Memory

Unified / managed memory：簡化 programming，不代表沒有成本

Unified memory 讓 host/device 可以用更統一的 address model，但底層可能涉及 page migration。若 CPU 與 GPU 反覆碰不同頁面，可能造成昂貴的 migration / page faults。

float *p = nullptr;
hipMallocManaged(&p, bytes);
// host and device can access p under managed-memory semantics
hipFree(p);

可搭配 prefetch 等方式讓資料在使用前移往適當 device，降低 unexpected migration。

「Unified memory automatically makes all memory access fast」是錯的。它主要改善 programming model；效能仍取決於 access pattern 與 migration。
Page 38 / 100Streams

HIP Stream：建立有順序的 asynchronous work queue

Stream 可以理解成一條命令隊列。同一 stream 中 operations 保持順序；不同 streams 則有機會重疊執行，實際是否 concurrency 仍取決於 hardware 與 dependency。

hipStream_t s;
hipStreamCreate(&s);
hipMemcpyAsync(d,h,bytes,hipMemcpyHostToDevice,s);
hipLaunchKernelGGL(kernel,grid,block,0,s,d,N);
hipStreamSynchronize(s);
hipStreamDestroy(s);
Default stream 適合初學；要 pipeline copy + compute 時才需要進一步使用多 stream。Associate 至少要認得 stream 是 concurrency / ordering 概念。
Page 39 / 100Async Pipeline

用 double buffering 想像 copy/compute overlap

資料量大時，可以把 dataset 切成 chunks：GPU 計算 chunk 0 的同時，另一個 stream 傳輸 chunk 1。這需要 pinned host memory、async copy 與多 stream 才比較有機會真正 overlap。

Time → Stream 0: H2D(A) | Kernel(A) | D2H(A) Stream 1: H2D(B) | Kernel(B) | D2H(B)

若所有步驟之間都插入 hipDeviceSynchronize()，就把 pipeline 強制序列化了。

先求正確，再求 overlap。Concurrency 增加時，也增加 race / lifetime / ordering bug 風險。
Page 40 / 100Chapter Drill

Memory 題目如何快速分類？

  1. 大量 global load/store 很慢：先看 coalescing、reuse、cache/LDS。
  2. Host↔Device 時間很長：減少 transfer、batch、pinned memory、async pipeline。
  3. Occupancy 太低：看 registers、LDS、block size。
  4. Shared memory 很慢：看 bank conflicts / synchronization。
  5. Unified memory 抖動：看 page migration / access locality / prefetch。
