Page 122 / 150Lab 3 · rocBLAS GEMM

Exercise 1：直接用 rocBLAS 跑 SGEMM

rocBLAS 的核心實驗是 FP32 GEMM：

C = α × op(A) × op(B) + β × C

rocblas_sgemm(handle, transA, transB,
              M, N, K,
              &alpha,
              d_A, lda,
              d_B, ldb,
              &beta,
              d_C, ldc);

Lab 使用 M=N=K=1024，workload 為：

FLOPs = 2 × M × N × K
      = 2,147,483,648 FLOPs
      ≈ 2.15 GFLOP

GPU timing 要用 HIP events 或在 CPU timer 前後同步，因為 kernel/library call 是 asynchronous。

Lab code review：初始化 C 時若寫 for (i=0; i<K*N; i++)，通用寫法應為 M*N。這次 M=K 所以看不出錯。另外 β=0.1 且重複 benchmark 會讓 C 每次都累積；效能測試可以，但 correctness test 建議 β=0 或每次 reset C。
Page 123 / 150GFLOPS · Peak

GFLOP 是工作量，GFLOPS 才是吞吐量

GFLOPS = FLOPs / seconds / 1e9
Efficiency = measured throughput / matching theoretical peak × 100%

比較 theoretical peak 時 datatype 必須一致：FP32 SGEMM 就比較 FP32 peak，不能拿 FP8 peak。小矩陣也未必能把大型 Instinct GPU 吃滿，因此 1024³ 的結果不能直接解讀成 GPU 只用了某個固定比例的「全部能力」。

Exercise 3：FFT → IFFT round-trip 驗證數值正確性

N = 8192
signal = torch.randn(N, dtype=torch.float32, device='cuda')
spectrum = torch.fft.fft(signal)

Module 4：從 library user 變成 GPU kernel programmer

HIP programmer 直接建立 Grid / Block / Thread；hardware 再把 threads 組成 wavefront 並映到 SIMD execution。

int i = blockIdx.x * blockDim.x + threadIdx.x;
int blocks = (N + threads - 1) / threads;
kernel<<<blocks, threads>>>(...);
Host: allocate → H2D → launch → check → D2H → verify ↓ Device: parallel kernel
★★★★★：global index、ceiling division、bounds check if (i<N)、asynchronous launch 是 HIP 最基本四件事。
Page 132 / 150Lab 4 · Vector Add

Part 1：Vector Add from Scratch

__global__ void vec_add(const float* A,
                        const float* B,
                        float* C, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) C[i] = A[i] + B[i];
}

vec_add<<<(N+255)/256, 256>>>(d_A,d_B,d_C,N);

N=2²⁰=1,048,576，256 threads/block，因此 4096 blocks；每個 float 4 bytes，一個 vector 為 4 MiB。

new[] host → hipMalloc device → hipMemcpy H2D → vec_add kernel → hipMemcpy D2H → verify → hipFree/delete[]
new[] 對 delete[]；hipMalloc 對 hipFree，不能混用。
Page 133 / 150HIP Errors · Async

Kernel launch error 與 execution error 要分開抓

kernel<<<grid, block>>>(...);
HIP_CHECK(hipGetLastError());
HIP_CHECK(hipDeviceSynchronize());
API主要用途
hipGetLastError()取得並清除 last runtime error；常用來抓 immediate launch/config error
hipDeviceSynchronize()等先前 GPU work 完成，讓 asynchronous execution error surface
hipMemcpy D2H同步 copy 會等待必要 work，但錯誤可能延後到這裡才看到

Debug 時可積極 synchronize，正式 performance code 則避免在每個 kernel 後都強制 host 停住。

看到「kernel launch 是 asynchronous」就要想到：CPU 下一行不代表 GPU 已做完；timing、debugging 與 dependency 都要考慮 synchronization / stream ordering。

Page 135 / 150Histogram · LDS · Atomic

Porting Lab 的 histogram 同時教了三個 parallel pattern

__shared__ int local_bins[256];

for (int i=threadIdx.x; i<256; i+=blockDim.x)
    local_bins[i]=0;
__syncthreads();

int idx = blockIdx.x*blockDim.x + threadIdx.x;
int stride = blockDim.x*gridDim.x;
for (int i=idx; i<N; i+=stride)
    atomicAdd(&local_bins[data[i]], 1);
__syncthreads();

for (int i=threadIdx.x; i<256; i+=blockDim.x)
    atomicAdd(&bins[i], local_bins[i]);
Pattern目的
Per-block shared histogram先在 LDS privatize，降低直接打 global bins 的 contention
grid-stride loop同一 thread 可處理 idx + total_threads × k
atomicAdd多 threads / blocks 同時更新相同 bin 時避免 race
Shared memory 很快 ≠ 不需要 atomic。Atomic 解決的是 correctness / race，不是 memory latency。
Page 136 / 150Portability Trap

為什麼不能把 blockDim.x 偷換成硬寫 32？

Histogram 裡的 stride 是「整個 block / grid 有多少 threads」，不是 warp size：

for (...; i += blockDim.x) ...
stride = blockDim.x * gridDim.x;

若 blockDim.x=256 卻硬寫 32，threads 會重疊處理相同 indices，甚至重複 merge histogram。

blockDim.x = threads per block warp / wavefront = hardware execution group 兩者不是同一件事

另外 CUDA 常見 warp=32；課程 CDNA3/4 mental model 是 Wave64。硬寫 32 的 algorithm 若真的依賴完整 warp semantics，移植時更要人工 review。

Source portability ≠ performance portability。HIPIFY 可以轉 API，但無法保證 hardcoded architecture assumptions 正確。
Page 137 / 150Lab 4 · Reduction

Part 3：Block Reduction = many values → one partial sum

__shared__ float sdata[256];
int tid = threadIdx.x;
int gid = blockIdx.x*blockDim.x + tid;
sdata[tid] = (gid < N) ? input[gid] : 0.0f;
__syncthreads();

for (int s=blockDim.x/2; s>0; s>>=1) {
    if (tid < s) sdata[tid] += sdata[tid+s];
    __syncthreads();
}
if (tid==0) output[blockIdx.x]=sdata[0];
256 values → 128 → 64 → 32 → 16 → 8 → 4 → 2 → 1

0.0f 是 sum 的 identity：有效資料不足一整個 block 時，其餘 threads 填 0 仍不改變總和。

__syncthreads() 是 block-level barrier。每一 stage 都要等前一 stage 的 sdata 更新完成，否則下一輪可能讀到舊值。
Page 138 / 150Multi-pass Reduction

1,048,576 → 4096 → 16 → 1，只需要三個 passes

current_size = N;
src = d_in;
dst = d_tmp1;
while (current_size > 1) {
    grid = (current_size + block - 1) / block;
    reduce_sum<<<grid, block>>>(src,dst,current_size);
    hipGetLastError();
    std::swap(src,dst);
    current_size = grid;
}
Pass 1: 1,048,576 → 4,096 partial sums Pass 2: 4,096 → 16 Pass 3: 16 → 1 final sum

同一 default stream 的 kernels 具有 ordering，因此每輪不必 host-side hipDeviceSynchronize。最後同步 D2H copy 會等 final result 完成。

原 Lab 配置了 d_tmp2 但實際未使用；真正 ping-pong 是 d_in ↔ d_tmp1。使用 std::swap 時較正規應 include <utility>。
Page 139 / 150Wavefront-aware

Lab 的 reduction 是正確 baseline，但還不算充分 wavefront-optimized

目前 kernel 從 256 一直降到 1，每輪都透過 LDS + __syncthreads()。這是易懂、正確的 block reduction baseline。

當剩下一個 wavefront 時，更進階版本可使用 wave shuffle / wave-level primitives 減少 LDS traffic 與 barrier overhead。

Block-wide stage: LDS + barrier ↓ 最後一個 wavefront ↓ wave-level reduction / shuffle ↓ partial sum
不要把 CUDA 最後 32 threads 的寫法原封不動搬到 CDNA Wave64。先確認 API / architecture semantics，再做 optimization。

Page 143 / 150Transpose · Baseline

為什麼 Matrix Transpose baseline 是「read 好、write 壞」？

out[x * H + y] = in[y * W + x];

C/C++ row-major 中，同一 row 的 columns 在 memory 連續。假設相鄰 threads x=0,1,2,3 且 y 固定：

Read:  in[y*W+0], in[y*W+1], in[y*W+2], in[y*W+3]
       → contiguous / coalesced

Write: out[0*H+y], out[1*H+y], out[2*H+y], out[3*H+y]
       → 每次跨 H elements / strided

Transpose 的數學要求是 B[col][row] = A[row][col]。原本同一 row 的連續資料在輸出變成同一 column，因此 direct global-memory implementation 天生容易一邊 coalesced、一邊 strided。

Copy 是 B[row][col]=A[row][col]；Transpose 必須交換 row/col。這個數學重新排列正是 strided write 的來源。
Page 144 / 150LDS Tiled Transpose

改善原理：把「轉方向」放到便宜的 LDS 裡

__shared__ float tile[TILE][TILE+1];

tile[threadIdx.y][threadIdx.x] = in[yIn*W + xIn];
__syncthreads();
out[yOut*H + xOut] = tile[threadIdx.x][threadIdx.y];
HBM input ↓ coalesced horizontal read LDS tile[y][x] ↓ __syncthreads() LDS read tile[x][y] ← 在 on-chip memory 裡換方向 ↓ remap output block x/y HBM output ↓ coalesced horizontal write

關鍵不是「用了 shared memory 所以快」，而是 LDS 當 staging/reordering area，讓昂貴的 global read/write 都變成較規則、可 coalesce 的 pattern。

Baseline = 橫著讀、直著寫；Tiled = 橫著讀進 LDS、LDS 裡轉方向、再橫著寫出去。
Page 145 / 150LDS Bank Conflicts

為什麼 tile 是 [TILE][TILE+1]？

tile[16][17] 的第 17 格不是有效 matrix 資料，而是 padding。目的不是 global coalescing，而是改變 LDS row stride，降低 transposed column-like access 落到相同 bank 的規律。

Coalescing → global/HBM transaction efficiency Bank conflict → LDS internal parallel access efficiency 兩者是不同層的問題

Threads 在 load phase 寫 tile[y][x]，store phase 讀 tile[x][y]，所以一定要在兩者中間放 block-wide __syncthreads()。

Barrier 要放在 bounds-check if 外面，避免 edge block 中只有部分 threads 抵達 barrier。

Part 3：FP32 vs FP16 vs BF16，不只看速度也要看誤差

FormatExponentFraction核心特性
FP32823高 precision、大 range
FP16510比 BF16 多 fraction bits，precision 較好
BF1687跟 FP32 相同 exponent width，dynamic range 大

GEMM 的工作量：

FLOPs = 2 × M × N × K
M=N=K=2048 → 17.18 GFLOP / GEMM

Reduced precision 常能使用更高吞吐的 matrix execution path；常見 mixed-precision concept 是低精度 operands 搭配較高精度 accumulation，以降低長 reduction 的累積誤差。

BF16 range 較好 ≠ BF16 precision 較好。FP16 fraction bits 較多；BF16 的主要優勢是 exponent range。
