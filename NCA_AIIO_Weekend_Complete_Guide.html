3. CPU、GPU 與 Accelerated Computing

比較CPUGPU
設計取向少量強核心、複雜控制、低單執行緒延遲大量平行運算單元、高吞吐
擅長OS、I/O、branch-heavy、general purposematrix/vector、相似操作、大量資料平行
記憶體大容量 DDR、較低頻寬HBM/GDDR，高頻寬但容量較有限
AI 角色資料載入、控制、排程、network stacktraining 與 inference compute
CPU：協調與控制＋GPU：大量平行計算＝Accelerated System

為什麼 GPU 適合 AI？

神經網路大量執行矩陣乘法、卷積、attention 等可平行化數值運算。GPU 可讓大量 thread 對不同資料元素執行相似指令，並利用高 memory bandwidth 餵資料。

Amdahl's Law 的直覺

只有可平行的部分能被 GPU 大幅加速。若 preprocessing、I/O 或 serial code 佔比高，整體 speedup 仍受限制。

陷阱：「GPU 永遠比 CPU 快」是錯的。小工作、分支很多、資料傳輸成本過高、無法平行化時，CPU 可能更適合。
Check 3：一個 workload 具有大量互不相依的矩陣運算，哪種處理器更合適？
答案：GPU，因為它針對高吞吐平行運算。

5. TensorRT 與推論最佳化

TensorRT 接收已訓練模型，針對 NVIDIA GPU 建立最佳化的 inference engine/runtime 執行路徑。它不是 training framework。

PyTorch / TensorFlow / ONNX→TensorRT Build & Optimize→Engine→GPU Inference

常見最佳化

技術作用注意
Layer / Tensor Fusion合併操作，減少 memory movement 與 kernel launch不一定所有 graph 都可融合
Kernel Auto-tuning為目標硬體與 shape 選擇高效 kernel建置 engine 可能需要時間
Quantization使用較低精度，降低 memory 與提高吞吐需評估 accuracy
Memory Optimization重用 buffer、規劃 tensor memory模型 shape 與 concurrency 會影響需求
Dynamic Shapes支援不同輸入尺寸需定義 optimization profiles

Precision

FP32 通常精度較高、資源較多；FP16/BF16/FP8/INT8 可降低 memory footprint 並提高效能。精度越低不代表一定越好，必須符合模型 accuracy 與硬體支援。

TensorRT vs Triton

TensorRTTriton Inference Server
最佳化和執行模型管理與提供模型服務
engine、kernel、precisionrequest、batching、concurrency、model repository
可被 Triton backend 使用可同時服務 TensorRT、PyTorch、ONNX 等 backend
Check 5：需求是透過 HTTP/gRPC 對外服務多個模型版本，應優先選什麼？
答案：Triton Inference Server；TensorRT 可作為其中一種最佳化 backend。

6. GPU 架構與記憶體

基本執行階層

Grid→Thread Blocks→Warps→Threads
名詞重點
SMStreaming Multiprocessor，GPU 的主要執行單元群組。
CUDA Core執行一般 FP/INT 運算的核心單元。
Tensor Core針對 matrix multiply-accumulate 的加速單元，對 AI 很重要。
Warp一組一起排程的 threads；分支差異會降低效率。
HBM高頻寬 GPU memory，適合大型模型與高資料吞吐。

Memory hierarchy

層級特性
Registers每個 thread 使用，速度最快、容量小。
Shared Memory / L1block 內共享，低 latency，可減少 global memory 存取。
L2 CacheGPU 跨 SM 共用 cache。
HBM / Global Memory容量大、頻寬高，但 latency 高於 on-chip memory。
Host Memory / Storage更遠；資料搬移可能成 bottleneck。

Compute-bound vs Memory-bound

Compute-bound：運算單元已飽和；Memory-bound：GPU 等資料，memory bandwidth 或資料存取成為限制。增加 FLOPS 不一定能解決 memory-bound workload。

AI 常見限制：模型大小受 GPU memory capacity 影響；運算速度常受 memory bandwidth、interconnect、batch size 與 precision 影響。
Check 6：GPU compute utilization 不高，但 memory bandwidth 已接近滿載，這較像哪一類 bottleneck？
答案：Memory-bound。

平台／元件定位直覺理解

HGX高密度多 GPU baseboard/reference platform由 OEM/ODM 整合成伺服器

PCIe、NVLink 的角色

PCIe 是通用 I/O interconnect，連接 CPU、GPU、NIC、NVMe；NVLink 聚焦高頻寬 accelerator communication。它們可同時存在，並非只能二選一。

DPU 的價值

  • Network packet processing 與 virtual switching offload
  • Storage services 與 data path acceleration
  • Security、encryption、zero-trust isolation
  • 將 infrastructure control plane 與 tenant/application 隔離
陷阱：DPU 不是用來取代 GPU 做模型 training。DPU 處理 infrastructure data path；GPU 處理 accelerated compute。
Check 7：OEM 想用 NVIDIA 多 GPU baseboard 整合自己的 server，最貼近哪個平台？
答案：HGX。

8. AI Networking：Ethernet、InfiniBand、RDMA、RoCE

技術用途／特色
Ethernet廣泛、成熟、與既有 data center 相容；AI cluster 可使用高速 Ethernet。
InfiniBand高吞吐、低 latency、成熟 RDMA 與 HPC/AI fabric 能力。
RDMA讓一台主機直接存取另一台主機 memory，降低 CPU involvement 與 copy。
RoCE在 Ethernet 上提供 RDMA；通常需要良好 lossless/congestion 設計。
GPUDirect RDMANIC 與 GPU memory 更直接交換資料，降低 host staging overhead。
NCCL在可用 interconnect 上提供 GPU collective operations。

Collective communication

Operation意義
Broadcast一個 rank 的資料傳給所有 ranks。
Reduce多個 ranks 的資料聚合到一個 rank。
AllReduce聚合後讓所有 ranks 都取得結果；分散式 training 常見。
AllGather每個 rank 收集所有 ranks 的資料。
ReduceScatter先 reduce，再把結果分片給各 rank。

為什麼 network 會限制 training？

資料平行 training 中，各 GPU 必須同步 gradients。當 GPU 計算越快、node 越多，communication overhead 越容易成為 scaling bottleneck。

題目線索：低 latency、HPC、native fabric → InfiniBand；既有 Ethernet、希望 RDMA → RoCE；multi-GPU gradients → NCCL/AllReduce；繞過 CPU copy → GPUDirect RDMA。
Check 8：分散式 training 每一步需要所有 GPU 取得合併後 gradient，對應哪個 collective？
答案：AllReduce。

Persistent Storage→Network / Data Fabric→Host Memory→GPU Memory→Compute

Training 與 Inference 的儲存需求

面向TrainingInference
主要資料大型 dataset、checkpoint、logsmodel weights、artifacts、input/output、cache
I/O 模式大量 parallel reads、periodic large writes快速 model loading、scale-out、多版本
失敗恢復checkpoint/restart 非常重要model replica、availability、快速重啟

Storage 類型

類型適合情境
Local NVMe低 latency cache/scratch；但 node-local、持久性與共享要另外設計。
Parallel File System大量 clients 與高 aggregate throughput，例如大型 training。
Object Storage大量非結構化資料、容量與 durability；常搭配 caching/data pipeline。
NFS簡單共享、較小規模；大型並行 workload 需確認效能。

GPU starvation

GPU utilization 低可能是 storage throughput 不足、data loader 太慢、network congestion、CPU preprocessing 或小檔 metadata overhead，而不是 GPU 故障。

規劃原則：Compute、network、storage 要一起 scale。只增加 GPU，資料供應能力不變，投資報酬率會快速下降。
Check 9：多 GPU training 時 GPU 經常等待下一批資料，第一步應檢查哪些層？
答案：Storage throughput、data pipeline、network、CPU preprocessing 與 data loader。

10. Data Center Power、Cooling 與 Facility

為什麼 AI rack 特別困難？

  • GPU 數量與單顆功耗高，rack power density 大幅提升。
  • 持續高負載使平均功耗接近峰值，不能只看 nameplate。
  • 電力、PDU、UPS、busway、冷卻與網路必須共同規劃。
  • 高溫、降頻、電力限制會直接影響 training time 與 throughput。

Air cooling vs Liquid cooling

項目Air CoolingLiquid Cooling
優點成熟、維護習慣普遍高熱密度效率較佳、可降低風扇需求
限制高密度 rack 可能受限CDU、管路、漏液偵測、facility 改造
監控inlet/outlet temp、fan、airflowflow、pressure、supply/return temp、leak

Power metrics

指標意義
Power draw即時／平均功耗。
Power cap限制元件或系統功耗，通常以效能換電力／散熱裕度。
PUEFacility total energy ÷ IT equipment energy；越接近 1 越有效率。
Thermal throttling溫度超過門檻時降低 clock，以保護硬體。
陷阱：Power capping 不等於關機。它是控制功耗與效能的手段；若 thermal/power emergency 才可能觸發更嚴格保護。
Check 10：GPU 溫度升高且 clock 自動下降，最可能是哪種現象？
答案：Thermal throttling。

Device Plugin

resources:
  limits:
    nvidia.com/gpu: 1

Device Plugin 讓 Kubernetes 辨識並分配 GPU。它不是 GPU driver，也不是 monitoring system。

MIG

Multi-Instance GPU 可把支援的 GPU 分割為具隔離資源的 instances，提高多租戶與小型 workload 利用率。MIG 不等於 time slicing；前者提供硬體層級資源分割，後者是時間共享。

Operator 核心：宣告 desired state，controller 持續觀察 actual state 並修正，不只是一次性安裝 script。

Operations 的四個循環

Scheduling

  • Bin packing：提高資源利用率。
  • Gang scheduling：分散式 job 所需多個資源同時就緒才啟動。
  • Topology awareness：把需要密集 communication 的 GPU 放在較佳拓撲。
  • Queue / priority / quota：公平性與重要任務優先。

MLOps

MLOps 把資料、模型與 deployment lifecycle 系統化：data/version control、training pipeline、validation、model registry、deployment、monitoring、drift、rollback。它不只是 DevOps 換名字，因為還必須管理資料與模型品質。

Fault domains 與 availability

設計 replica、node/rack/fabric fault domain、checkpoint、rolling upgrade、health checks，避免單一元件失效讓整個 AI service 中斷。

Check 12：模型 latency 正常但 accuracy 隨時間下降，最應關注哪類問題？
答案：Data/model drift 與模型品質監控，而不只是 GPU health。

14. 情境題解法與常見陷阱

四步解題法

  1. 找目標：是效能、部署、監控、硬體管理、網路還是儲存？
  2. 找層級：Model、runtime、node、cluster、OOB、facility？
  3. 找關鍵字：AllReduce、serving、Prometheus、firmware、latency 等。
  4. 排除越界選項：不要用 monitoring 工具解 deployment；不要用 BMC 解 model drift。

十個高頻陷阱

  1. TensorRT 是 inference，不是 training。
  2. Triton 是 serving，不是 GPU driver。
  3. NCCL 是 collective communication，不是 network hardware。
  4. GPU Operator 管 software lifecycle，不取代 BMC。
  5. DCGM 是 GPU management/telemetry，不是整個 application APM。
  6. 低 GPU utilization 不代表 GPU 故障。
  7. InfiniBand 與 Ethernet 都可用於 AI；依需求選擇。
  8. GPU memory capacity 與 bandwidth 是不同限制。
  9. Power cap 會影響 performance，但未必造成 shutdown。
  10. MIG 是 partition；不是把多張 GPU 合成一張。

最後 30 分鐘背誦

  1. Training 更新 weights；Inference 使用 weights。
  2. Latency 是一次多久；Throughput 是一秒多少。
  3. GPU 擅長平行數值運算；CPU 擅長控制與 general-purpose。
  4. TensorRT 最佳化；Triton 提供服務。
  5. NCCL 做 AllReduce；RDMA 降低 CPU/copy overhead。
  6. Storage 太慢會讓 GPU starvation。
  7. GPU Operator 管 K8s software；BMC 管 OOB hardware。
  8. DCGM 看 GPU；Prometheus 收 metrics；Grafana 顯示。
  9. MIG 是 GPU partition，不是 aggregation。
  10. 任何 AI cluster 都要同時看 compute、network、storage、power、cooling。
